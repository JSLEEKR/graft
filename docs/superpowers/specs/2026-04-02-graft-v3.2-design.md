# Graft v3.2 Design Spec

## Goals

Parser error recovery, LSP polish, and correctness fixes. v3.2 transforms the parser from throw-on-first-error to error-accumulating, enabling multi-error diagnostics in the LSP. Remaining scope addresses LSP completion gaps (import names, storage values, cache eviction), tech debt from v3.1, and deferred bug fixes. No breaking changes; no new syntax.

## Lessons from v3.1 Applied

- **DIRECT tier as default** (R-PROC-01): 8 consecutive DIRECT rounds with zero failures confirms the tier is calibrated. Only parser error recovery needs debate.
- **Merged Step 3+4 permanent** (R-PROC-02): validated across 5 versions. No split needed.
- **Cross-critique removed from MEDIUM** (R-PROC-08): 15 consecutive skips with zero quality cost. Formally removed from the process. Adversarial checklist in Step 1 replaces it entirely.
- **Streamlined artifacts** (R-PROC-09): DIRECT and TEST-ONLY rounds produce no harness files. Debated rounds produce only convergence report + review result.
- **Adversarial checklist expanded** (R-PROC-10): new categories added: missing data sources in scope lookups, platform-specific encoding, LSP-specific edge cases (cursor position, partial tokens, document sync timing).

## Architecture Changes

### Parser Contract Change (R-04)

**Before (v3.1)**: Parser throws `GraftError` on first error. Caller catches it. LSP shows one error at a time.

**After (v3.2)**: Parser returns `{ program: Program | null, errors: GraftError[] }`. On recoverable errors, the parser skips to the next statement boundary and continues. The returned Program is partial (may have missing/malformed declarations but is structurally valid). On unrecoverable errors (e.g., completely malformed input), program is null.

Recovery strategy: **panic mode at declaration boundaries**. When the parser encounters an unexpected token inside a declaration, it:
1. Records the error with location
2. Advances tokens until it finds a top-level keyword (context, node, memory, graph, edge, import) or EOF
3. Resumes normal parsing from that keyword

This approach is well-established in compiler literature (Dragon Book Ch. 4.1.4) and matches the Graft grammar's structure: all top-level declarations start with distinct keywords, making synchronization points unambiguous.

**Downstream impact**:
- `compileToProgram()`: already accumulates analyzer errors; now also accumulates parser errors. Returns partial results on parse errors (same as it does for scope/type errors today).
- LSP `validateDocument()`: shows all errors at once. No code change needed if compileToProgram returns errors correctly.
- CLI `compile`/`check`: shows all errors. Minor formatting adjustment.

**Ratchet implications**:
- [v2.2-R10] "Parser/lexer remain throw-based" -- MUST be unlocked. Parser moves to error accumulation. Lexer remains throw-based (lexer errors are rare and usually unrecoverable).
- [v3.0-R27] "PARSE_UNEXPECTED_TOKEN and PARSE_MISSING_FIELD on parser throws" -- compatible. These error codes are retained; they are now accumulated instead of thrown.

### LSP Cache Eviction (TD-02)

Add LRU eviction to the server.ts `cache` Map. When cache exceeds N entries (configurable, default 50), evict least-recently-accessed entries. Track access time on get/set. Simple timestamp-based eviction; no external dependencies.

## Error Code Changes

No new error codes. Existing `PARSE_UNEXPECTED_TOKEN` and `PARSE_MISSING_FIELD` are reused for accumulated errors. The parser error recovery does not introduce new error types -- it changes the delivery mechanism (accumulation vs throw).

## Breaking Changes

None. All changes are additive or internal:
- Parser return type changes from `Program` to `ParseResult` but this is internal to compiler.ts. The public API (`compileToProgram`, `compile`, `compileAndGenerate`) maintains the same contract.
- LSP improvements are backward compatible (new completions, not changed completions).
- Sub-path export addition (`./format`) is additive.
