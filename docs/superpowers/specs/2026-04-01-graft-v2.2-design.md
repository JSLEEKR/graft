# Graft v2.2 — Design Spec: npm Distribution + LSP Server

## 1. Goals

Make Graft installable and usable as a standard npm package, and provide a Language Server Protocol (LSP) server for IDE integration. Additionally, address high-priority tech debt and deferred items from v2.0/v2.1 retrospectives.

1. **npm distribution** — publish `graft` to npm with correct package.json metadata, bin entry, prepublish scripts, and README badges
2. **LSP server** — expose Graft diagnostics, hover info, and go-to-definition via LSP for VS Code and other editors
3. **Tech debt cleanup** — eliminate double-parse, decompose executor, fix version strings
4. **Correctness gaps** — foreach binding collision detection, conditional edge transform warnings

### Scope boundary decisions

- **Failure strategies (R-04)**: Despite being HIGH priority in retro-technical, this is a significant runtime feature that conflicts with v2.2's distribution focus. The executor currently aborts on failure (v1.2-R07 ratchet). Implementing retry/fallback/skip requires rethinking flow execution, which belongs in v3.0 alongside async I/O and multi-backend work. The ratchet v1.2-R07 remains locked.
- **Memory importability (R-01)**: Requires unlocking v2.0-R13. Deferred to v3.0 where multi-backend storage backends also need import semantics.
- **A-05 (single-graph enforcement)**: v2.2 adds a warning (C-03) but does not add graph selection. Graph selection is a v3.0 feature.

### 4.2 Double-Parse Elimination (D-01)

**Current problem** (TD-01): `compiler.ts` lexes+parses the source, then if imports exist, calls `resolve(source, sourceFile)` which re-lexes and re-parses the same source internally.

**Fix**: Change `resolve()` signature to accept the already-parsed `Program` and entry file path:

```typescript
// Before
export function resolve(source: string, sourceFile: string): ResolveResult;

// After
export function resolve(
  entryProgram: Program,
  sourceFile: string,
  fileReader?: FileReader,
): ResolveResult;
```

The resolver skips parsing the entry file and uses the provided `Program` directly. It still parses imported files internally (those haven't been parsed yet). The `compiler.ts` passes `program` to `resolve()` instead of `source`.

**Impact**: Every file with imports goes from 2 parses to 1 parse for the entry file. Imported files are still parsed once each (no change).

### 4.3 Executor Decomposition (D-02)

Extract from `executor.ts` (475 lines) into two new modules:

**`src/runtime/prompt-builder.ts`** (~80 lines):
- `buildPrompt(nodeDecl, program, outputs, memoryDir): string`
- `buildContextSection(contextName, sessionDir, memoryDir, program): string`
- Depends on: `Program`, `NodeDecl`, filesystem reads

**`src/runtime/flow-runner.ts`** (~120 lines):
- `runSequential(nodes, executor): Promise<NodeResult[]>`
- `runParallel(branches, executor): Promise<NodeResult[]>`
- `runForeach(foreachNode, executor): Promise<NodeResult[]>`
- Depends on: `Executor` (passed as interface/callback for node execution)

**`executor.ts`** reduced to ~275 lines:
- Session lifecycle (clean, setup)
- Node execution orchestration (delegates to flow-runner)
- Output storage
- Token tracking integration
- Imports from prompt-builder and flow-runner

### 4.4 ProgramIndex Utility (D-03)

**New file: `src/program-index.ts`**

```typescript
import { Program, ContextDecl, NodeDecl, MemoryDecl, EdgeDecl, GraphDecl } from './parser/ast.js';

export class ProgramIndex {
  readonly contextMap: Map<string, ContextDecl>;
  readonly nodeMap: Map<string, NodeDecl>;
  readonly memoryMap: Map<string, MemoryDecl>;
  readonly edgeMap: Map<string, EdgeDecl[]>;  // source name -> edges
  readonly graphMap: Map<string, GraphDecl>;

  constructor(program: Program) {
    this.contextMap = new Map(program.contexts.map(c => [c.name, c]));
    this.nodeMap = new Map(program.nodes.map(n => [n.name, n]));
    this.memoryMap = new Map(program.memories.map(m => [m.name, m]));
    this.edgeMap = new Map();
    for (const edge of program.edges) {
      const existing = this.edgeMap.get(edge.source) ?? [];
      existing.push(edge);
      this.edgeMap.set(edge.source, existing);
    }
    this.graphMap = new Map(program.graphs.map(g => [g.name, g]));
  }

  getContext(name: string): ContextDecl | undefined { return this.contextMap.get(name); }
  getNode(name: string): NodeDecl | undefined { return this.nodeMap.get(name); }
  getMemory(name: string): MemoryDecl | undefined { return this.memoryMap.get(name); }
  getEdgesFrom(source: string): EdgeDecl[] { return this.edgeMap.get(source) ?? []; }
  getGraph(name: string): GraphDecl | undefined { return this.graphMap.get(name); }
}
```

**Migration**: Replace manual Map construction in `ScopeChecker`, `TypeChecker`, `TokenEstimator`, `Executor` with `ProgramIndex`. Each class takes `ProgramIndex` in constructor (or constructs it internally from `Program`).

### 4.5 Structured Error Codes (D-04)

Add an optional `code` field to `GraftError`:

```typescript
export type GraftErrorCode =
  // Scope errors
  | 'SCOPE_DUPLICATE_NAME'
  | 'SCOPE_UNDEFINED_REF'
  | 'SCOPE_INVALID_WRITES'
  | 'SCOPE_BINDING_COLLISION'    // NEW for C-01
  // Type errors
  | 'TYPE_FIELD_NOT_FOUND'
  | 'TYPE_SCHEMA_MISMATCH'
  | 'TYPE_MAX_TOKENS_INVALID'
  // Import errors
  | 'IMPORT_CIRCULAR'
  | 'IMPORT_NOT_FOUND'
  | 'IMPORT_NAME_NOT_FOUND'
  // Parse errors
  | 'PARSE_UNEXPECTED_TOKEN'
  | 'PARSE_MISSING_FIELD'
  // General
  | 'GRAPH_MISSING'
  | 'GRAPH_MULTIPLE'             // NEW for C-03
  | 'TRANSFORM_ON_CONDITIONAL';  // NEW for C-02

export class GraftError extends Error {
  readonly severity: 'error' | 'warning';
  readonly location: SourceLocation;
  readonly code?: GraftErrorCode;  // NEW

  constructor(
    message: string,
    location: SourceLocation,
    severity?: 'error' | 'warning',
    code?: GraftErrorCode,
  ) { ... }
}
```

Error codes are optional for backward compatibility. New diagnostics should include codes; existing diagnostics get codes added incrementally. LSP maps `code` to `DiagnosticCode` for IDE display.

### 4.6 Source File Tracking (D-05)

Add `sourceFile?: string` to `ContextDecl` and `NodeDecl` in `ast.ts`:

```typescript
export interface ContextDecl {
  // ... existing fields ...
  sourceFile?: string;  // NEW: populated by resolver for imported declarations
}

export interface NodeDecl {
  // ... existing fields ...
  sourceFile?: string;  // NEW: populated by resolver for imported declarations
}
```

The resolver sets `sourceFile` on each declaration it merges into the entry program. Declarations from the entry file get `sourceFile` set to the entry file path. This enables LSP go-to-definition for imported symbols.

### 4.7 Correctness: Foreach Binding Collision (C-01)

In `ScopeChecker`, when checking foreach FlowNodes:

```
For each foreach FlowNode:
  binding = foreachNode.binding
  if binding in nodeNames or binding in producesNames or binding in contextNames or binding in memoryNames:
    warning("Foreach binding '{binding}' collides with declaration '{binding}'")
```

This prevents the runtime's `outputs.set(binding, ...)` from silently overwriting a node output.

### 4.8 Correctness: Conditional Edge Transform Warning (C-02)

In the analyzer (ScopeChecker or TypeChecker), when checking edges:

```
For each edge:
  if edge.target.kind !== 'direct' and edge.transforms.length > 0:
    warning("Transforms on conditional edge '{source} -> ...' are parsed but not applied at runtime", code: 'TRANSFORM_ON_CONDITIONAL')
```

### 4.11 LSP Server (L-01 through L-04)

**New directory: `src/lsp/`**

The LSP server is a standalone Node.js process that communicates via JSON-RPC over stdio. It uses the `vscode-languageserver` and `vscode-languageserver-textdocument` npm packages.

**`src/lsp/server.ts`** — main LSP server entry point:

```typescript
import {
  createConnection,
  TextDocuments,
  ProposedFeatures,
  InitializeParams,
  TextDocumentSyncKind,
  DiagnosticSeverity,
} from 'vscode-languageserver/node.js';
import { TextDocument } from 'vscode-languageserver-textdocument';
import { compile } from '../compiler.js';

const connection = createConnection(ProposedFeatures.all);
const documents = new TextDocuments(TextDocument);

connection.onInitialize((params: InitializeParams) => ({
  capabilities: {
    textDocumentSync: TextDocumentSyncKind.Full,
    hoverProvider: true,
    definitionProvider: true,
  },
}));

// Validate on open/change
documents.onDidChangeContent((change) => {
  validateDocument(change.document);
});

function validateDocument(doc: TextDocument): void {
  const source = doc.getText();
  const result = compile(source, doc.uri);
  const diagnostics = [
    ...result.errors.map(e => toDiagnostic(e, DiagnosticSeverity.Error)),
    ...result.warnings.map(w => toDiagnostic(w, DiagnosticSeverity.Warning)),
  ];
  connection.sendDiagnostics({ uri: doc.uri, diagnostics });
}
```

**Diagnostics (L-02)**:
- Every `GraftError` from `compile()` is converted to an LSP `Diagnostic`
- `severity` maps to `DiagnosticSeverity.Error` or `DiagnosticSeverity.Warning`
- `location` maps to LSP `Range` (line/column to Position)
- `code` (from D-04) maps to `Diagnostic.code` for filtering

**Hover info (L-03)**:
- On hover over a context name: show field list with types and `max_tokens`
- On hover over a node name: show model, budget, reads, writes, produces
- On hover over a memory name: show field list, `max_tokens`, `storage`
- Uses `ProgramIndex` (D-03) for O(1) lookups

**Go-to-definition (L-04)**:
- On go-to-definition for an identifier in `reads`, `writes`, or import list: navigate to the declaration
- For imported symbols: navigate to the `sourceFile` location (requires D-05)
- Uses `ProgramIndex` and `sourceFile` field for cross-file navigation

### 4.12 VS Code Extension Skeleton (L-05)

Create a minimal VS Code extension in `editors/vscode/`:

```
editors/vscode/
  package.json          — extension manifest
  language-configuration.json — bracket matching, comments, auto-closing
  syntaxes/graft.tmGrammar.json — TextMate grammar for .gft syntax highlighting
```

The extension:
- Registers `.gft` as the Graft language
- Provides syntax highlighting via TextMate grammar (keywords, strings, numbers, comments)
- Launches `graft-lsp` as the language server
- Published separately to VS Code marketplace (not part of npm package)

The VS Code extension is a separate publishable artifact. The npm package includes only the `graft-lsp` binary. Any LSP-compatible editor can use `graft-lsp` directly.

## 6. Non-Goals (deferred to v3.0+)

- Failure strategies (retry/fallback/skip) in executor
- Memory importability across files
- Async file I/O in executor
- Source maps for generated output
- Multi-backend compilation targets
- Field-level writes / multi-field partial reads
- Dollar-cost tracking
- Memory encryption / versioning / migration
- SQLite/Redis memory storage backends
- Hard budget abort
- Auto-budget adjustment from actuals
- LSP completions (autocomplete for identifiers) — potential v2.3 addition
- LSP rename/refactoring support
- LSP code actions (quick fixes)
