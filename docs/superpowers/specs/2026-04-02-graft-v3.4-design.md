# Graft v3.4 Design Specification

**Date**: 2026-04-02
**Version**: 3.4.0
**Theme**: LSP rename support, estimator completeness, LSP refinements

## Overview

v3.4 completes the LSP maturation arc with rename support (the last major missing LSP feature for multi-file editing), fixes a correctness gap in token estimation for conditional edges, and addresses tech debt in features.ts (552 lines, predicted split threshold in v3.2 retro).

## Features

### F-01: LSP Rename Support

**Priority**: HIGH (Rank 1 in v3.3 retro)
**Complexity**: MEDIUM

Add `textDocument/rename` and `textDocument/prepareRename` handlers.

**Semantics**:
- Rename contexts, nodes, memories, and graphs
- Single-file: rename all references (reads, writes, edges, graph flows, produces)
- Cross-file: rename imported names in all files that import the renamed declaration
- Use ProgramIndex for reference collection within a file
- Use workspace export cache for cross-file import reference discovery
- prepareRename validates the cursor is on a renameable symbol

**Scope boundaries**:
- Only top-level declaration names (contexts, nodes, memories, graphs) are renameable
- Field names are NOT renameable (too many interaction points)
- Edge names are NOT renameable (edges are anonymous, identified by source/target)
- Import aliases are not supported (Graft has no aliases)

### F-02: Token Estimation for Conditional Edges

**Priority**: MEDIUM (Rank 2 in v3.3 retro)
**Complexity**: LOW

Fix estimator.ts to account for conditional edge branches.

**Semantics**:
- Best case: cheapest conditional branch (minimum cost among all when/else targets)
- Worst case: most expensive conditional branch (maximum cost among all when/else targets)
- Skip conditional edges where target is 'done' (terminal)
- ~20-30 lines in computeFlowCosts()

### F-03: features.ts Split

**Priority**: MEDIUM (Rank 4 in v3.3 retro, TD-02)
**Complexity**: LOW

Split features.ts (552 lines) into focused modules.

**Structure**:
- `features/diagnostics.ts` — getDiagnostics, extractUndefinedName
- `features/hover.ts` — getHoverInfo, KEYWORD_DOCS, formatType
- `features/completions.ts` — getCompletions + all helpers
- `features/definition.ts` — getDefinitionLocation
- `features/symbols.ts` — getDocumentSymbols
- `features/code-actions.ts` — buildAutoImportEdit, computeRelativeImportPath
- `features/index.ts` — re-export all public functions

Server.ts imports change from `./features.js` to `./features/index.js`.

### F-04: Hierarchical Document Symbols

**Priority**: MEDIUM (Rank 3 in v3.3 retro)
**Complexity**: LOW

Extend getDocumentSymbols() to return nested symbols with children.

**Semantics**:
- Context children: field names (SymbolKind.Field)
- Node children: produces fields (SymbolKind.Field), reads/writes entries (SymbolKind.Property)
- Memory children: field names (SymbolKind.Field)
- Graph children: flow node references (SymbolKind.Function)
- Edge: no children (already flat)

### F-05: Code Action Handler Extraction

**Priority**: LOW-MEDIUM (Rank 5 in v3.3 retro, TD-03)
**Complexity**: LOW

Move code action matching logic from server.ts to a pure function in features/code-actions.ts.

## Non-Goals

- Memory importability (deferred, needs design discussion)
- Additional code actions beyond auto-import
- Async file I/O
- Source maps
- Field renaming
