# Graft v5.0 Design Spec — Quality + Unification Release

## Version Theme

v5.0 is a **quality and unification** release. It resolves the biggest tech debt from v4.x (formatExpr duplication, Condition/Expr duality, evaluateCondition bypass, ratchet accumulation) without adding new user-facing language features. The expression system architecture is preserved; this version removes redundancy, unifies code paths, and cleans up common_memory.

## Feature Specifications

### F1: formatExpr Extraction

**Retro refs**: TD-01, design retro 2C

**Problem**: Two byte-for-byte identical `formatExpr` implementations exist:
- `src/lsp/features/hover.ts:101-120` (exported)
- `src/codegen/orchestration.ts:188-207` (private copy)

**Solution**: Extract `formatExpr` to `src/format.ts` (which already contains `formatTokenReport` per v3.1-R10). Both hover.ts and orchestration.ts import from there.

**Affected files**:
- `src/format.ts` — add `formatExpr(expr: Expr): string`
- `src/lsp/features/hover.ts` — remove local `formatExpr`, import from `../format.ts`
- `src/codegen/orchestration.ts` — remove private `formatExpr`, import from `../format.ts`

**Constraints**:
- The function signature must remain `(expr: Expr) => string`
- All 8 current Expr kinds must be handled (literal, field_access, binary, unary, group, call, template, conditional)
- No behavioral change; this is a pure extraction

**Tests**: Existing tests cover formatExpr behavior. Add 1-2 import verification tests.

### F2: Condition -> Expr Unification

**Retro refs**: Design retro 1D, technical retro E-06, TD-04

**Problem**: The `Condition` interface (ast.ts:174-178) is a separate type from `Expr`, with `left: Expr`, `op` (6 operators), and `value: string | number | boolean`. This causes:
1. `Condition.value` is a flat literal, not an `Expr` -- edge conditions cannot use expressions on the right side
2. `evaluateCondition` and `evalCondition` are separate functions from `evaluateExpr`
3. `conditionFieldName()` exists solely as a bridge between the two type systems

**Solution**: Replace `Condition` with a binary `Expr`. An edge condition `when score >= 5` becomes:
```typescript
// Before
{ left: { kind: 'field_access', segments: ['score'], location }, op: '>=', value: 5 }

// After — just a binary Expr
{ kind: 'binary', op: '>=',
  left: { kind: 'field_access', segments: ['score'], location },
  right: { kind: 'literal', value: 5, location },
  location }
```

**AST changes** (`src/parser/ast.ts`):
- `ConditionalBranch.condition` changes from `Condition | undefined` to `Expr | undefined`
- `Transform` filter type: `condition: Condition` changes to `condition: Expr`
- `Condition` interface: DEPRECATED and REMOVED
- `conditionFieldName()` function: REMOVED

**Parser changes** (`src/parser/parser.ts`):
- `parseCondition()` now returns an `Expr` (binary) instead of a `Condition`
- The parser still restricts edge condition syntax: `<field> <op> <literal>` parsed as a binary Expr with field_access left and literal right
- No change to what syntax is accepted -- only the AST representation changes

**Analyzer changes**:
- `src/analyzer/types.ts`: `checkConditionTypes` operates on `Expr` (binary) instead of `Condition`. Extracts field name from `expr.left` (field_access) directly, no longer needs `conditionFieldName()`
- `src/analyzer/scope.ts`: condition validation uses Expr checking (already partially done via `checkExprSources`)
- `src/analyzer/graph-checker.ts`: no change (does not reference Condition type)

**Runtime changes**:
- `src/runtime/flow-runner.ts`: `evaluateCondition` REMOVED. Condition evaluation delegates to `evaluateExpr` which already handles binary expressions with all 6 comparison operators
- `src/runtime/transforms.ts`: `evalCondition` REMOVED. Filter transform evaluation uses `evaluateExpr`

**Codegen changes**:
- `src/codegen/hooks.ts`: condition display uses `formatExpr` (from F1) instead of `conditionFieldName`

**Constraints**:
- The 6 condition operators (>=, >, <, <=, ==, !=) are already in the binary op union -- no new operators needed
- Edge condition parsing remains restricted to `<field> <op> <literal>` at the parser level (no arbitrary expressions in edge conditions yet)
- All existing edge condition tests must continue to pass with the new AST representation
- `mkCond()` test helper (v4.0-R14) must be updated to produce binary Expr instead of Condition

**Ratchet implications**:
- v4.0-R03 (`Condition.left: Expr`) becomes moot -- Condition type removed entirely
- v4.0-R04 (`conditionFieldName bridge`) already UNLOCKED -- function now removed
- v3.3-R06 (`evaluateCondition exported`) -- function removed, replaced by evaluateExpr
- v3.3-R07 (`FlowContext.getConditionalEdge`) -- unchanged, but condition field type changes
- v4.2-R11 (`evalCondition loose equality`) -- removed with evalCondition

### F3: evaluateCondition/evalCondition Merger (part of F2)

**Retro refs**: TD-04, design retro 2B

This is a direct consequence of F2. Once `Condition` becomes `Expr`, the separate evaluation functions are eliminated:

- `evaluateCondition(condition, outputs, variables)` in flow-runner.ts -- REMOVED. Call sites use `evaluateExpr(condition, outputs, variables)` instead.
- `evalCondition(condition, item)` in transforms.ts -- REMOVED. Filter transform uses `evaluateExpr(condition, new Map(Object.entries(item)))`.

**Key behavioral preservation**:
- Variable-first resolution: already in `evaluateExpr` (v4.0-R24)
- Loose equality for == and != operators: preserved in `evaluateExpr` (v4.5-R04), then changed to strict in F4
- Numeric coercion for ordered operators: already in `evaluateExpr`
- Undefined field handling: `evaluateExpr` returns `undefined` for missing fields, which evaluates correctly with comparison operators

### F4: Loose Equality Fix

**Retro refs**: TD-03, R-REVISIT-02

**Problem**: `evaluateExpr` (expr-eval.ts:68-69) uses JavaScript loose equality (`==`/`!=`), causing `0 == false` to be `true`, `"" == false` to be `true`, `null == undefined` to be `true`. These JS-specific coercion rules produce surprising results for a DSL.

**Solution**: Change to strict equality (`===`/`!==`).

**Affected files**:
- `src/runtime/expr-eval.ts`: lines 68-69, change `==` to `===` and `!=` to `!==`

**Behavioral changes**:
- `0 == false` -> `false` (was `true`)
- `"" == false` -> `false` (was `true`)
- `null == undefined` -> `false` (was `true`)
- `null == null` -> `true` (unchanged)
- `5 == 5` -> `true` (unchanged)
- `"hello" == "hello"` -> `true` (unchanged)

**Constraints**:
- This is a **breaking change** for edge conditions that relied on loose equality (e.g., `when field == 0` matching when field is `false`). This is acceptable because the loose behavior was a JS artifact, not intentional DSL semantics.
- The `??` null coalescing operator already uses strict null/undefined checking (v4.7-R04), so this aligns with existing strict-null semantics.
- Update all tests that relied on loose equality behavior.

**Ratchet implications**:
- v4.5-R04 (`equality uses == loose`) -- UNLOCKED and replaced with strict equality
- v4.2-R11 (`evalCondition loose equality`) -- moot after F2 removes evalCondition

### F5: Exhaustive Switch Mandate

**Retro refs**: Design retro 1A, P-05 (technical retro)

**Problem**: Not all Expr switch dispatchers have exhaustive `never` default guards. v4.1-R2 added them to FlowNode switches (flow-runner, estimator, scope) but Expr switches in some locations lack them.

**Solution**: Add exhaustive `never` default to ALL functions that switch on `Expr.kind`:
- `src/runtime/expr-eval.ts` (`evaluateExpr`)
- `src/analyzer/graph-checker.ts` (`checkExprSources`)
- `src/analyzer/types.ts` (`inferExprType`, `checkExprTypeErrors`)
- `src/format.ts` (`formatExpr` -- after F1 extraction)

**Pattern**:
```typescript
default: {
  const _exhaustive: never = expr;
  throw new Error(`Unhandled expr kind: ${(expr as any).kind}`);
}
```

**Constraints**:
- TypeScript compiler will enforce completeness at compile time
- No runtime behavioral change (all cases are already handled)
- This is a compile-time safety net for future Expr kind additions

### F6: Ratchet Archival + Common Memory Compression

**Retro refs**: Process retro 4.1, 4.4, 5.4, 5.5

**Problem**: Common memory has ~684 lines with ~326 ratchets. Many are implementation-detail ratchets (e.g., "Star token in lexer -- LOCKED") that will never be contested. This creates context pressure for long sessions.

**Solution**: Archive v3.x (v3.0 through v3.9) and v4.0-v4.4 ratchets to `harness/archived_ratchets.md`. Retain in active common_memory:
- v4.5-v4.9 ratchets (most recent, may still be referenced)
- All DESIGN ratchets (cross-cutting decisions, not implementation details)
- All Review Feedback entries
- All Recurring Patterns and Debate ROI entries
- Notes for Future

**Classification criteria**:
- **DESIGN ratchet** (keep): Affects multiple pipeline stages, establishes a pattern, or constrains future decisions. Examples: "Variable-first resolution order" (v4.0-R21), "Expr 5-kind discriminated union" (v4.0-R01), "FlowNode 5 kinds" (v4.0-R11).
- **IMPL ratchet** (archive): Single-file change, mechanical addition, or implementation detail. Examples: "Star token in lexer" (v4.3-R01), "AmpAmp token in lexer" (v4.6-R01), any individual operator/token/precedence ratchet.

**Target**: Reduce common_memory.md from ~684 lines to ~300 lines.

**Affected files**:
- `harness/common_memory.md` — remove archived sections, add summary references
- `harness/archived_ratchets.md` — append v3.x and v4.0-v4.4 IMPL ratchets

## Migration Strategy

### Test Migration for F2 (Condition -> Expr)

The `Condition` type is used in test helpers and assertions across many test files. The migration approach:

1. Update `mkCond()` helper in `tests/helpers.ts` to return a binary `Expr` instead of `Condition`
2. Update all test files that construct `Condition` objects directly
3. Update test assertions that check `condition.value` (now `expr.right.value` for literal)
4. Search for all `Condition` type imports and replace with `Expr`

The parser-level syntax does not change -- `when field >= 5` still works. Only the AST representation changes internally.

### Breaking Change for F4 (Strict Equality)

Loose equality (`==`) changing to strict (`===`) is a semantic change. All tests with equality assertions need review:
- Tests comparing numbers to strings that relied on coercion
- Tests comparing null/undefined that relied on loose nullish matching
- Edge condition tests with `== 0` or `!= ""` patterns

The `??` operator (v4.7) already uses strict null checks, so this aligns the equality operators with existing null-handling semantics.
