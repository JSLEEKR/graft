# Graft v3.3 Design Spec

## Goals

LSP code actions, conditional edge runtime routing, document symbols, and condition type validation. v3.3 completes the two highest-priority gaps identified in the v3.2 technical retrospective: auto-import code actions (EP-02, ranked #1) and conditional edge runtime execution (R-05, ranked #2). Smaller additions round out the version with document symbols (#3) and condition type validation (TD-06, #4). No breaking changes; no new syntax keywords.

## Lessons from v3.2 Applied

- **DIRECT tier as default** (R-PROC-01): 11 consecutive no-debate rounds with zero failures. Only LSP code actions (new handler type + workspace scanning) needs debate.
- **Merged Step 3+4 permanent** (R-PROC-02): validated across 6 versions. No split needed.
- **Cross-critique permanently removed** (R-PROC-08): 19 consecutive eligible rounds with zero quality loss. Adversarial checklist in Step 1 is the sole mechanism.
- **Streamlined artifacts** (R-PROC-09): DIRECT and TEST-ONLY rounds produce no harness files. Validated over 11 consecutive rounds.
- **Adversarial checklist** (R-PROC-10): no expansion needed for v3.3. Current categories (error path coverage, platform encoding, LSP edge cases) cover all v3.3 features.
- **Pre-round tech debt verification** (R-PROC-11): NEW. Before scoping tech debt items, verify each against the codebase. Prevents R3-style waste from v3.2 (TD-05 already implemented).
- **Merge single-item rounds** (R-PROC-12): NEW. If a round reduces to fewer than 2 substantive changes, fold into an adjacent round.

## Architecture Changes

### Code Actions Handler (EP-02)

**New LSP capability**: `textDocument/codeAction` handler registered in server.ts alongside existing diagnostic, hover, completion, and definition handlers.

**Workspace file scanning**: When the LSP server initializes (or when files change), scan the workspace for `.gft` files. For each file, parse it and extract exported names (contexts and nodes, per v2.0-R13). Cache the results in a `Map<string, string[]>` keyed by file path. Invalidate on file change events.

**Code action flow**:
1. Client sends `textDocument/codeAction` with diagnostics at cursor range
2. Server filters for diagnostics with code `SCOPE_UNDEFINED_REF`
3. For each undefined reference, search the workspace cache for files exporting that name
4. For each match, generate a `CodeAction` with:
   - Title: `Import '${name}' from "${relativePath}"`
   - Kind: `quickfix`
   - Edit: insert `import { ${name} } from "${relativePath}"` at the correct position
5. Import insertion position: after the last existing import statement, or at line 0 if no imports exist. If imports exist, insert after the last `import` line with a newline separator.

**Design decisions**:
- One code action per importable file (if the name exists in multiple files, offer all as separate actions)
- Relative path calculation: from the current document to the target file, always with `.gft` extension
- No auto-import on completion (only via code action on diagnostic). This keeps completions simple.
- Workspace scan is lazy: triggered on first code action request if cache is empty, then maintained incrementally via didChange/didOpen/didClose notifications

### Conditional Edge Runtime (R-05)

**Current state**: flow-runner.ts `executeFlowNodes()` walks FlowNode[] and handles `kind: 'node'` steps. When an edge has `target.kind === 'conditional'`, the runtime currently does not evaluate conditions -- conditional edges are effectively dead code at runtime.

**After v3.3**: When the flow runner encounters a node whose outgoing edge has conditional branches, it evaluates each `when` branch condition against the source node's output:

```
function evaluateCondition(condition: Condition, output: Record<string, unknown>): boolean {
  const fieldValue = output[condition.field];
  switch (condition.op) {
    case '==': return fieldValue == condition.value;
    case '!=': return fieldValue != condition.value;
    case '>=': return Number(fieldValue) >= Number(condition.value);
    case '>':  return Number(fieldValue) > Number(condition.value);
    case '<=': return Number(fieldValue) <= Number(condition.value);
    case '<':  return Number(fieldValue) < Number(condition.value);
  }
}
```

**Branch selection**: iterate `when` branches in order. First branch whose condition evaluates to true is selected. If no branch matches, the `else` branch is used. If no `else` branch exists and no condition matches, skip the edge (log a warning).

**Integration point**: in `executeFlowNodes()`, after a node completes execution and produces output, check if the next edge is conditional. If so, evaluate conditions against the output to determine which target node to execute next.

### Document Symbols (EP-05)

**New LSP capability**: `textDocument/documentSymbol` handler in server.ts.

**Implementation**: Use ProgramIndex data to return all declarations as `DocumentSymbol` objects. Map declaration types to LSP SymbolKind:

| Graft Declaration | LSP SymbolKind |
|-------------------|----------------|
| ContextDecl | Class |
| NodeDecl | Function |
| MemoryDecl | Variable |
| GraphDecl | Module |
| EdgeDecl | Event |

Each symbol includes name, kind, range (from SourceLocation), and selection range. Children are not needed for the initial implementation (flat list of top-level declarations).

**Data source**: ProgramIndex maps (contextMap, nodeMap, memoryMap, graphMap, edgesBySource). All declarations already have SourceLocation with line/column/length.

### Condition Type Validation (TD-06)

**New validation in TypeChecker**: When checking edge conditions, validate that the comparison operator is compatible with the field's type.

**Rules**:
- `>=`, `>`, `<=`, `<` (ordered comparisons): valid only on `Int` and `Float` type fields
- `==`, `!=` (equality comparisons): valid on all types (`Int`, `Float`, `String`, `Bool`)
- If an ordered comparison is used on a `String` or `Bool` field, emit a `TYPE_CONDITION_MISMATCH` error

**Error code**: Add `TYPE_CONDITION_MISMATCH` to the `TypeErrorCode` sub-union in `GraftErrorCode`. This is the first new error code since v3.0-R6.

**Location**: TypeChecker is the correct place (type compatibility is a type-checking concern, not a scope concern). The check runs during edge condition validation, after field existence has been confirmed by ScopeChecker.

## Error Code Changes

| Code | Sub-union | Description |
|------|-----------|-------------|
| `TYPE_CONDITION_MISMATCH` | TypeErrorCode | Ordered comparison operator used on non-numeric field |

GraftErrorCode member count: 180 ratchets reference "30+ members with sub-unions" (v3.0-R6). Adding TYPE_CONDITION_MISMATCH brings the union to its next member.

## Breaking Changes

None. All changes are additive or internal:
- New LSP handlers (codeAction, documentSymbol) are opt-in by client capability
- Conditional edge routing adds runtime behavior where none existed (previously dead code)
- TYPE_CONDITION_MISMATCH is a new diagnostic that flags previously-silent invalid code
- No public API contract changes
- No syntax changes

## Backward Compatibility

- Programs that previously compiled without errors will continue to compile, UNLESS they use ordered comparisons on String/Bool fields (TYPE_CONDITION_MISMATCH). This is intentional: these programs were silently incorrect.
- Runtime behavior changes only for programs with conditional edges, which were previously not executed at runtime. All existing test programs without conditional edges are unaffected.
- LSP clients that do not support code actions or document symbols will see no change.
