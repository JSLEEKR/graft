# Graft v4.2 Design Spec — Expression Functions & Runtime Consistency

## Version Goal

Add built-in expression functions (`len()`, `max()`, `min()`, `str()`), unify equality semantics between routing and transforms, and close remaining exhaustive switch gaps. This is a targeted feature + quality release.

## Scope

### IN

1. **Expression functions** (deferred from v4.0): `len(list)`, `max(a, b)`, `min(a, b)`, `str(value)` as built-in functions callable in expressions.
   - New Expr kind: `call` with `name: string` and `args: Expr[]`
   - Parser: `parsePrimary` recognizes `Identifier + LParen` as function call (currently this is only used for graph calls at flow level)
   - Evaluator: `evaluateExpr` handles `call` kind with built-in dispatch
   - Type checker: validates argument count and types per function
   - Scope checker: validates function names against a whitelist (no user-defined functions)
   - LSP: function name completions, hover docs

2. **Equality semantics unification** (retro-technical finding 2a): `evalCondition` in transforms.ts uses strict equality (`===`/`!==`) while `evaluateCondition` in flow-runner.ts uses loose equality (`==`/`!=`). Unify on loose equality to match Graft's stringly-typed condition values.

3. **Remaining exhaustive switches** (retro-technical finding 3a): Add `never` defaults to:
   - `applyOne` in transforms.ts (switches on Transform.type)
   - `evaluateExpr` binary op switch in flow-runner.ts

4. **Graph call return values** (retro-technical finding 6c): Graph calls currently execute but discard output. Enable `let result = Sub() -> ...` by capturing the final node's output from child execution and exposing it in parent scope.

### OUT

- Multiplication/modulo operators — no demand (v4.0-R02 ratchet, flat precedence intentional)
- Variable mutation/reassignment — `let` is immutable binding
- Memory importability (v2.0-R13) — no demand
- User-defined functions — built-in whitelist only
- String interpolation — template literals deferred
- Graph call memory isolation (retro-technical finding 4) — shared memory writes are intentional
- Lambda/anonymous graph declarations — v5.0+
- TD-05 through TD-10 (all LOW, permanent carry)

## Technical Notes

### Expression Functions

New Expr kind:
```typescript
interface ExprCall {
  kind: 'call';
  name: string;
  args: Expr[];
  location: SourceLocation;
}
```

Built-in function registry:
```typescript
const BUILTIN_FUNCTIONS: Record<string, { arity: number | [number, number]; returnType: InferredType }> = {
  len: { arity: 1, returnType: 'number' },
  max: { arity: 2, returnType: 'number' },
  min: { arity: 2, returnType: 'number' },
  str: { arity: 1, returnType: 'string' },
};
```

Parser change: In `parsePrimary`, when an identifier is followed by `LParen`, check if it's a builtin function name. If yes, parse as function call expression. If no, it remains a field_access segment (existing behavior). This distinguishes `len(x)` (function call) from `NodeName(args)` (graph call, only at flow level).

### Graph Call Return Values

Currently `executeFlowNodes` case `graph_call` executes child flow and discards results. Change:
1. Capture the last NodeResult from child execution
2. Store it in `ctx.outputs.set(graphCallName, lastResult.output)`
3. This enables `let x = Sub().field -> ...` patterns

### Equality Unification

In transforms.ts `evalCondition`, change `===`/`!==` to `==`/`!=` to match flow-runner.ts `evaluateCondition`. This ensures filter conditions behave identically to routing conditions.

## Ratchet Impact

### Anticipated Unlocks
- **[v4.0-R01] Expr: 5-kind discriminated union** — gains 6th kind (`call`). No unlock needed (union is extensible by design).

### New Ratchets Expected
- Expression function whitelist (4 built-in functions)
- ExprCall AST node design
- Function arity validation in type checker
- Graph call output capture pattern
- Equality semantics: loose equality for all condition evaluation

## Process Rules

- R1 (functions): MEDIUM tier — new Expr kind + parser changes + runtime evaluation
- R2 (graph return + equality + switches): DIRECT tier — targeted fixes
- R3 (LSP + integration): DIRECT tier — LSP updates for function calls + integration tests
- R4 (regression): TEST-ONLY tier — standard integration round
