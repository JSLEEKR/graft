# Graft v4.4 Design Spec — Expression Extraction + String Interpolation

## Overview

v4.4 addresses the two highest-priority items from the v4.3 technical retrospective:
1. **evaluateExpr extraction** — flow-runner.ts at 404 lines, past the 400-line threshold
2. **String interpolation** — template expressions in let bindings: `"Score: ${A.score}"`

Additionally: BUILTIN_FUNCTIONS descriptor enrichment (consolidate 4-consumer scatter) and common memory archival.

## Feature 1: evaluateExpr Extraction

### Goal
Extract `evaluateExpr`, `resolveNestedField`, and builtin dispatch from `flow-runner.ts` into `src/runtime/expr-eval.ts`.

### Design
- New file: `src/runtime/expr-eval.ts`
  - Exports: `evaluateExpr`, `resolveNestedField`
  - Contains: all expression evaluation logic (~90 lines)
- `flow-runner.ts` imports from `expr-eval.ts`
- `transforms.ts` imports `resolveNestedField` from `expr-eval.ts`
- All existing test imports from `flow-runner.ts` continue to work via re-export

### Constraints
- Pure refactor: zero behavioral changes
- All existing tests must pass unchanged (re-exports from flow-runner.ts)
- flow-runner.ts drops from ~404 to ~320 lines

## Feature 2: String Interpolation

### Goal
Support template expressions in let bindings: `let msg = "Score: ${A.score}"`

### Syntax
```graft
graph G(input: In, output: Out, budget: 10k) {
  A -> let msg = "Result: ${A.score} out of ${max(A.total, 100)}"
     -> B -> done
}
```

### Design

#### Lexer
- New token: `TemplateString` — triggered by `"` when followed by content containing `${`
- Template parts are lexed as: TemplateStart, content segments, expressions, TemplateEnd
- Alternative (simpler): lex entire `"..${..}.."` as single TemplateString token, parse internally

#### AST
- New Expr kind: `template`
```typescript
| { kind: 'template'; parts: TemplatePart[]; location: SourceLocation }

type TemplatePart =
  | { kind: 'text'; value: string }
  | { kind: 'expr'; value: Expr }
```

#### Parser
- In parsePrimary: when encountering a string literal containing `${`, parse as template
- Template parsing: split on `${...}`, parse each `...` as an expression via parseExpr

#### Runtime
- evaluateExpr template case: evaluate each part, concatenate as strings
- Parts with kind 'text' → literal string
- Parts with kind 'expr' → evaluateExpr → String()

#### Type Checker
- Template expressions always infer to 'string' type
- Inner expressions can be any type (auto-converted via String())

#### LSP
- No special handling needed (templates are expressions)

### Constraints
- Nested templates NOT supported: `"${" inner ${x}"}"` is invalid
- Escape: `\${` produces literal `${` (no interpolation)
- Empty interpolation `${}` is a parse error

## Feature 3: BUILTIN_FUNCTIONS Descriptor Enrichment

### Goal
Consolidate the 4-consumer scatter by adding `returnType` and `description` to the registry.

### Design
```typescript
export const BUILTIN_FUNCTIONS: Record<string, {
  arity: number;
  returnType: 'number' | 'string' | 'unknown';
  description: string;
  signature: string;
}> = {
  len: { arity: 1, returnType: 'number', description: 'Returns length of array or string', signature: 'len(value) → number' },
  // ...
};
```

### Impact
- `inferExprType` reads `returnType` from registry instead of hardcoded switch
- `hover.ts` reads `signature` + `description` from registry instead of FUNC_DOCS
- `evaluateExpr` runtime implementation stays in expr-eval.ts (too varied for registry)
- Reduces future per-builtin touch points from 4-5 to 2 (registry + runtime impl)

## Feature 4: Common Memory Archival

### Goal
Archive T1-v2.2 ratchets to reduce common_memory.md cognitive load.

### Design
- New file: `harness/archived_ratchets.md` — T1-T6 + v1.2-v2.2 ratchets
- common_memory.md replaces those sections with: `See harness/archived_ratchets.md for T1-v2.2 ratchets`
- Active ratchets remain: v3.0+ only
- Reduces common_memory.md from ~650 lines to ~450 lines

## Scope Boundaries

**IN**: evaluateExpr extraction, string interpolation, BUILTIN_FUNCTIONS enrichment, memory archival
**OUT**: user-defined functions, conditional expressions (ternary), new builtins, budget enforcement
