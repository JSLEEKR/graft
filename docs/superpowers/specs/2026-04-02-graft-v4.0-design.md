# Graft v4.0 Design Specification

**Date**: 2026-04-02
**Version**: 4.0.0
**Theme**: Language evolution -- variables, expressions, and graph composition

## Overview

v3.x delivered the complete runtime foundation: all flow control constructs, failure strategies, field-level operations, full LSP tooling (8 features), npm distribution, and diagnostic specialization. The codebase is clean (890 tests, ~235 ratchets, zero MEDIUM/HIGH tech debt). v4.0 is a major version that evolves the Graft language itself -- new grammar productions, new AST node types, and new runtime semantics.

The technical retro (v3.9) recommended **Option A: Language Evolution** as the v4.0 direction. The rationale: the runtime is feature-complete for current semantics; the parser and pipeline are modular and ready for extension; the highest-value work is expanding what `.gft` files can express.

v4.0 introduces three language features:

1. **Variables** -- `let` bindings in graph flow blocks for intermediate data extraction
2. **Expressions** -- arithmetic, string concatenation, and field access expressions usable in variable assignments and edge conditions
3. **Graph parameters** -- parameterized graph declarations for reusable pipeline templates

Together these transform Graft from a static pipeline declaration language into a language with data flow control. Pipelines can extract intermediate results, compute derived values, and compose reusable sub-pipelines.

## Features

### F-01: Variables (`let` bindings in graph flow)

**Syntax**:
```graft
graph Pipeline(Input -> Output, budget: 50k) {
  Analyzer
  let score = Analyzer.analysis.confidence
  let threshold = 0.7
  edge Analyzer -> when score >= threshold: Reviewer
                   else: Rewriter
  Reviewer -> done
  Rewriter -> Reviewer
}
```

**Semantics**:
- `let <name> = <expr>` declares a variable in the graph flow block
- Variables are evaluated at runtime after the preceding node completes
- Variable values are extracted from node outputs (field access) or literal values
- Variables are scoped to the enclosing graph (not visible across graphs)
- Variables can be referenced in edge conditions (replacing raw field references)
- Variables are immutable -- no reassignment after declaration
- Variable names must not collide with node names, context names, memory names, or other variable names in the same graph

**AST changes**:
- New `FlowNode` kind: `{ kind: 'let'; name: string; value: Expr; location?: SourceLocation }`
- `FlowNode` discriminated union grows from 3 to 4 kinds
- `Condition.field` can reference a variable name (resolved at runtime)

**Parser changes**:
- New keyword: `let`
- `parseFlowNode()` handles `let` as a new case
- `parseExpr()` new recursive descent production (see F-02)

**Analyzer changes**:
- ScopeChecker: variable name collision detection (against nodes, contexts, memories, graphs, other variables)
- ScopeChecker: variable must be declared before use in conditions
- ScopeChecker: variable source must reference a declared node's produces field
- TypeChecker: variable type inferred from source expression, validated against condition usage

**Runtime changes**:
- `executeFlowNodes` handles `let` kind: evaluates expression against current outputs, stores in variable map
- Variable map passed to `evaluateCondition` for field resolution
- Variables resolved before node outputs in condition evaluation (explicit binding takes precedence)

**Estimator changes**:
- `let` nodes have zero token cost (data extraction, no LLM call)
- Variable type information feeds into downstream condition estimation

### F-02: Expressions

**Syntax**:
```graft
let total = Analyzer.analysis.word_count + Editor.edits.additions
let label = "Result: " + Analyzer.analysis.summary
let ratio = Analyzer.analysis.score / 10.0
let items = Analyzer.analysis.findings
```

**Expression grammar** (recursive descent):
```
Expr       = Additive
Additive   = Unary (('+' | '-') Unary)*
Unary      = ('-' | '!') Unary | Primary
Primary    = NumberLiteral | StringLiteral | BoolLiteral | FieldAccess | '(' Expr ')'
FieldAccess = Identifier ('.' Identifier)*
```

**Design decisions**:
- No multiplication/division in v4.0 -- addition and subtraction cover the primary use cases (aggregation, threshold adjustment). Multiplication/division deferred to v4.1+ if demand emerges.
  - **UPDATE**: Include `/` (division) for ratio computation (`score / 10.0`). Exclude `*` (multiplication) -- less common in pipeline data flow.
- No function calls in v4.0 -- `len()`, `max()`, `min()` deferred. Expressions are for data extraction and simple arithmetic, not general computation.
- String concatenation via `+` (same operator as numeric addition, type-dependent behavior). Type mismatch in `+` is a compile-time error (no implicit coercion).
- Boolean negation via `!` for condition inversion.
- Parenthesized expressions for grouping.
- Field access is the primary expression form: `NodeName.produces.field` resolves to the output of a previously-executed node.

**AST changes**:
- New `Expr` type (discriminated union):
  ```
  Expr =
    | { kind: 'literal'; value: string | number | boolean; location: SourceLocation }
    | { kind: 'field_access'; segments: string[]; location: SourceLocation }
    | { kind: 'binary'; op: '+' | '-' | '/'; left: Expr; right: Expr; location: SourceLocation }
    | { kind: 'unary'; op: '-' | '!'; operand: Expr; location: SourceLocation }
    | { kind: 'group'; inner: Expr; location: SourceLocation }
  ```

**Lexer changes**:
- New tokens: `Plus` (+), `Minus` (-) -- currently not in the token set
- Existing tokens reused: `Slash` (/ -- already exists for budget syntax), `LParen`/`RParen`, `Dot`, `IntegerLiteral`, `FloatLiteral`, `StringLiteral`, `True`/`False`
- `Bang` (!) -- new token for boolean negation

**Parser changes**:
- New `parseExpr()`, `parseAdditive()`, `parseUnary()`, `parsePrimary()` productions
- `parsePrimary` handles literals, field access (dot-separated identifiers), and parenthesized sub-expressions

**Condition extension**:
- `Condition` interface updated: `field` replaced by `left: Expr` for the left-hand side
- Right-hand side remains a literal value (string | number | boolean) for v4.0
- This is a **breaking change** to the `Condition` interface -- existing code that reads `condition.field` must read `condition.left` instead

### F-03: Graph Parameters

**Syntax**:
```graft
graph ReviewPipeline(Input -> Output, budget: 30k, reviewer: Node, depth: Int = 1) {
  Analyzer
  edge Analyzer -> reviewer
  reviewer -> done
}

graph Main(TaskSpec -> FinalOutput, budget: 100k) {
  Planner
  ReviewPipeline(reviewer: SeniorReviewer, depth: 2)
  Planner -> ReviewPipeline -> done
}
```

**Semantics**:
- Graph declarations can have named parameters after the budget clause
- Parameters have a name, a type (`Node`, `Int`, `String`, `Bool`), and an optional default value
- `Node` parameters allow passing node references for composition (the primary use case)
- Primitive parameters (`Int`, `String`, `Bool`) allow configuration
- When a parameterized graph is used as a flow step, arguments are provided in parentheses
- Graph instantiation creates a scoped execution context: the called graph's flow is executed with parameter bindings resolved
- A parameterized graph without all required arguments is a compile-time error

**AST changes**:
- `GraphDecl` gains `params: GraphParam[]`
  ```
  GraphParam = { name: string; type: 'Node' | 'Int' | 'String' | 'Bool'; default?: string | number | boolean; location: SourceLocation }
  ```
- New `FlowNode` kind: `{ kind: 'graph_call'; name: string; args: GraphArg[]; location?: SourceLocation }`
  ```
  GraphArg = { name: string; value: Expr; location: SourceLocation }
  ```
- `FlowNode` discriminated union grows from 4 to 5 kinds (with F-01)

**Parser changes**:
- `parseGraphDecl()` extended to parse parameter list after budget
- New `parseGraphCall()` production for flow nodes that reference a graph with arguments
- Disambiguation: a bare identifier in flow is a node reference; identifier followed by `(` is a graph call

**Analyzer changes**:
- ScopeChecker: validate all required graph parameters are provided at call site
- ScopeChecker: validate parameter types match argument types
- ScopeChecker: validate `Node` parameter arguments reference declared nodes
- ScopeChecker: detect recursive graph calls (graph calls itself directly or indirectly)
- TypeChecker: graph parameter type checking (primitives match, Node references exist)

**Runtime changes**:
- `executeFlowNodes` handles `graph_call` kind: resolves parameters, creates child execution scope, delegates to the called graph's flow
- Node parameters resolve to actual NodeDecl references at runtime
- Primitive parameters are available as variables in the called graph's scope
- Budget partitioning: child graph execution is bounded by the child graph's declared budget (not the parent's remaining budget)

**Estimator changes**:
- Graph call estimation: estimates the called graph's cost using its declared budget and flow structure
- Recursive call detection mirrors scope checker (prevents infinite estimation loops)
- Graph parameter `Node` arguments: cost estimated from the referenced node's budget

## Breaking Changes

v4.0 introduces the following breaking changes (justifying the major version bump):

1. **`Condition.field` replaced by `Condition.left: Expr`**: All consumers of the `Condition` interface must update. The `field` string is replaced by a `field_access` expression. Migration: `condition.field` becomes `(condition.left as FieldAccessExpr).segments.join('.')` or similar.

2. **`FlowNode` union expands**: From 3 kinds (`node`, `parallel`, `foreach`) to 5 kinds (`node`, `parallel`, `foreach`, `let`, `graph_call`). All exhaustive switches on `FlowNode.kind` must add the new cases. This is technically non-breaking for consumers using default cases, but the `@graft-lang/graft/types` export changes.

3. **New keywords**: `let` becomes a reserved keyword. Any `.gft` file using `let` as an identifier (node name, field name, etc.) will fail to parse. Impact: low -- `let` is not a natural name for Graft declarations.

4. **`GraphDecl.params` field**: The GraphDecl interface gains a new required field. Consumers constructing GraphDecl objects must include `params: []`.

## Non-Goals

- Memory importability (v2.0-R13 -- no user demand, defer to v4.1+)
- Token budget hard enforcement (v2.1-R15 -- advisory model sufficient)
- Multiplication operator (defer to v4.1+ if demand)
- Function calls in expressions (`len()`, `max()`) -- defer to v4.1+
- Lambda/anonymous graph declarations -- defer to v5.0+
- Variable reassignment/mutation -- Graft variables are immutable
- Async I/O, source maps, workspace support (orthogonal to language evolution)
- Second codegen backend (no user demand)
- New LSP features (LSP is mature at 8 features; however, new language constructs will need completion/hover/definition support updates within existing features)
- TD-05 through TD-10 (all LOW, permanent carry -- see R-PROC-19 justification from v3.9)

## Ratchet Impact

### Anticipated Unlocks

- **[v2.2-R08] GraftErrorCode union**: Will gain new error codes for expression type errors, variable scope errors, graph parameter errors. The union is extensible by design (sub-union pattern from v3.0-R6). No unlock needed.
- **[v3.3-R06] evaluateCondition with 6 operators**: Must be extended to accept `Expr` left-hand side instead of field string. May need unlock if the function signature changes fundamentally.
- **[v3.3-R07] FlowContext.getConditionalEdge**: Unchanged -- the conditional edge system is orthogonal to how conditions reference their left-hand values.

### New Ratchets Expected

- Expression AST type design (Expr union)
- Variable scoping rules (graph-local, immutable)
- Graph parameter type system (Node | Int | String | Bool)
- Expression evaluation order (left-to-right, short-circuit for boolean)
- Parser precedence rules for expressions

## LSP Impact

All three features require LSP updates within existing feature modules (no new modules needed):

- **Completions**: `let` keyword in flow blocks, variable names in condition contexts, graph names with parameter hints, expression field access
- **Hover**: Variable declarations show inferred type, graph parameters show type and default
- **Definition**: Variable references navigate to `let` declaration, graph call navigates to graph declaration
- **Rename**: Variables renameable within graph scope
- **References**: Variable references tracked across graph flow
- **Diagnostics**: New error codes for expression type errors, variable scope errors, graph parameter errors

These updates are integrated into the implementation rounds (not separate LSP rounds) since the LSP feature modules follow the pure function pattern and each update is small.
