### R1: LSP Code Actions (Auto-Import) -- MEDIUM complexity

**Justification**: Introduces a new LSP handler type (`textDocument/codeAction`) that has no existing pattern in the codebase. Requires workspace-level file scanning and caching -- a new capability not present in any prior LSP feature. Has design decisions around: import insertion position, relative path calculation, workspace scan trigger strategy, and interaction with existing diagnostics. Two agents needed: A2-Pragmatist for minimal implementation path, A3-Skeptic for edge cases (multiple files exporting same name, circular imports, workspace scan performance, stale cache).

**Retro items addressed**: EP-02 (retro-technical #1, highest-value LSP feature), EP-02a/b/c from design spec. Also addresses TD-07 from retro-technical (features.ts approaching split threshold at 487 lines -- code actions should go in a separate function or R1 should split features.ts).

**Ratchet unlocks required**: None. No existing ratchets block code actions. v2.0-R13 (only ContextDecl and NodeDecl importable) is compatible -- code actions will only suggest importing contexts and nodes.

**Agent assignment**:
- Step 1: A2-Pragmatist + A3-Skeptic (2 agents, with adversarial checklist per R-PROC-04+R-PROC-10)
- Step 2: Removed (R-PROC-08)
- Step 3+4: Convergence + Implementation (1 agent, merged)
- Step 5: Reviewer (1 agent)

**Scope**:

1. **textDocument/codeAction handler in server.ts** (EP-02a)
   - Register `codeActionProvider: { codeActionKinds: [CodeActionKind.QuickFix] }` in server capabilities
   - Handler receives `CodeActionParams` with document URI, range, and context (including diagnostics)
   - Filter diagnostics for those with `code === 'SCOPE_UNDEFINED_REF'`
   - For each matching diagnostic, extract the undefined name from the diagnostic message
   - Query workspace cache for files exporting that name
   - Return `CodeAction[]` with workspace edits to insert import statements

2. **Workspace importable name cache** (EP-02b)
   - New data structure in server.ts: `Map<string, { exports: string[], lastModified: number }>` keyed by file URI
   - Population: on first code action request (lazy), scan workspace root for `.gft` files
   - For each file: read, lex, parse (using existing pipeline), extract exported names (context and node names per v2.0-R13)
   - Incremental update: on `didOpen`/`didChangeWatchedFiles`/`didSave`, re-parse the affected file and update its cache entry
   - On `didClose` or file deletion: remove from cache
   - Performance: parse is lightweight (lexer + parser only, no analyzer). Workspace of 50 files is ~50ms total.

3. **Import insertion logic** (EP-02c)
   - Find the last import statement in the document (scan lines for `import {`)
   - Insert new import on the line after the last import
   - If no imports exist, insert at line 0 (before first declaration)
   - Format: `import { Name } from "./relative/path.gft"`
   - Relative path: computed from current document URI to target file URI
   - If multiple files export the same name, generate one code action per file (user picks)

4. **Name extraction from diagnostic** (EP-02 implementation detail)
   - SCOPE_UNDEFINED_REF diagnostic message contains the undefined name
   - Extract via regex or structured data (if diagnostic.data is available)
   - Fallback: extract the word at the diagnostic range from the document text

**Test targets**:
- Code action for undefined ref that exists in another file -> offers import
- Code action for undefined ref that exists in multiple files -> offers multiple imports
- Code action for undefined ref that exists nowhere -> no code actions offered
- Import insertion after existing imports (correct position)
- Import insertion in file with no imports (line 0)
- Workspace cache populated on first request
- Workspace cache updated on file change
- No code actions for non-SCOPE_UNDEFINED_REF diagnostics
- Relative path calculation (same directory, subdirectory, parent directory)

**Estimated new tests**: ~15
**Estimated agent calls**: 4

### R2: Conditional Edge Runtime Routing -- DIRECT

**Justification**: The parser already parses conditional edges (v1.0+), the scope checker already validates them (v2.2-R3 SCOPE_TRANSFORM_CONDITIONAL), the codegen already handles them. The only gap is runtime evaluation in flow-runner.ts. This is a well-scoped additive change: add an `evaluateCondition()` function and a branch selection step in `executeFlowNodes()`. Follows the existing FlowContext pattern. No new abstractions needed.

The retro recommended MEDIUM for R2, but the actual implementation scope is narrow: one new function (~20 lines) and one integration point in the existing flow runner loop. The Condition type already exists in ast.ts with field/op/value. Downgraded to DIRECT per tier calibration (additive feature following established patterns, 11-round DIRECT streak with zero failures).

**Retro items addressed**: R-05 (retro-technical #2, deferred since v1.3). Completes a feature that has been partially implemented across parser, analyzer, and codegen since v1.0.

**Ratchet unlocks required**: None.

**Agent assignment** (DIRECT tier):
- Step 3+4: Implementer (1 agent)
- Step 5: Reviewer (1 agent)

**Scope**:

1. **evaluateCondition() function in flow-runner.ts** (R-05a)
   - Pure function: `evaluateCondition(condition: Condition, output: Record<string, unknown>): boolean`
   - Reads `condition.field` from `output` object
   - Applies `condition.op` (`==`, `!=`, `>=`, `>`, `<=`, `<`) against `condition.value`
   - Numeric comparisons: coerce both sides to Number for ordered operators
   - Equality comparisons: use loose equality (`==`) to handle string/number coercion
   - Missing field in output: treat as `undefined`, fails all comparisons except `!= value`

2. **Branch selection in executeFlowNodes()** (R-05b)
   - After a node completes and produces output, check if the outgoing edge has conditional branches
   - Edge structure: `target.kind === 'conditional'` with `target.when: { condition, target }[]` and `target.else?: string`
   - Iterate `when` branches in declaration order. First match wins.
   - If no `when` branch matches: use `else` target if present, otherwise skip (log warning, continue flow)
   - Selected target: execute the target node as the next step in the flow

3. **Integration with existing flow runner**
   - The existing `walkFlowNodes()` in scope checker already validates conditional edge structure
   - flow-runner.ts currently ignores conditional targets -- change from ignore to evaluate
   - No changes to executor.ts, prompt-builder.ts, or any other runtime file
   - Read source node output from FlowContext.outputs map (already populated after node execution)

**Test targets**:
- evaluateCondition: each operator (==, !=, >=, >, <=, <) with matching and non-matching values
- evaluateCondition: missing field returns false (except !=)
- evaluateCondition: numeric coercion for ordered operators
- Branch selection: first matching when branch selected
- Branch selection: else branch used when no when matches
- Branch selection: no else and no match -> skip with warning
- End-to-end: graph with conditional edge executes correct branch based on output

**Estimated new tests**: ~12
**Estimated agent calls**: 2

### R3: Document Symbols + Condition Type Validation -- DIRECT

**Justification**: Two small, independent features merged into a single round per R-PROC-12. Document symbols is ~30-50 lines of straightforward ProgramIndex-to-LSP mapping (retro-technical estimated LOW complexity). Condition type validation is ~20-30 lines in TypeChecker (retro-technical estimated LOW complexity). Neither involves design decisions -- both have clear specifications. DIRECT tier per R-PROC-01.

**R-PROC-11 verification**: TD-06 (condition type compatibility) verified against codebase. The TODO comment at `src/analyzer/types.ts:54` (`// TODO: condition type compatibility -- e.g., >= on String fields (v2)`) is confirmed to still exist per retro-technical TD-05. The validation is genuinely missing.

**Retro items addressed**: EP-05 (retro-technical #3, document symbols), TD-06 (retro-technical #4, condition type validation, deferred since v1.0).

**Ratchet unlocks required**: None.

**Agent assignment** (DIRECT tier):
- Step 3+4: Implementer (1 agent)
- Step 5: Reviewer (1 agent)

**Scope**:

1. **textDocument/documentSymbol handler** (EP-05)
   - Register `documentSymbolProvider: true` in server capabilities
   - Handler receives `DocumentSymbolParams` with document URI
   - Use cached ProgramIndex (from server.ts cache) to collect all declarations
   - Map each declaration to `DocumentSymbol`:
     - `name`: declaration name
     - `kind`: ContextDecl -> Class, NodeDecl -> Function, MemoryDecl -> Variable, GraphDecl -> Module, EdgeDecl -> Event
     - `range`: from SourceLocation (startLine, startCol to endLine, endCol)
     - `selectionRange`: same as range (name-only range could be refined later)
   - Return flat `DocumentSymbol[]` (no nesting for initial implementation)
   - Edge symbols: use format `"source -> target"` or `"source -> conditional"` as the symbol name
   - If no cached program exists for the URI, return empty array

2. **Condition type validation in TypeChecker** (TD-06)
   - Add `TYPE_CONDITION_MISMATCH` to `TypeErrorCode` sub-union in GraftErrorCode
   - In TypeChecker, add a check for edge conditions (iterate edges with conditional targets)
   - For each `when` branch condition:
     - Look up the source node's produces type (via ProgramIndex.producesFieldsMap)
     - Look up the field referenced by `condition.field`
     - If the operator is `>=`, `>`, `<=`, or `<` and the field type is not `Int` or `Float`:
       - Emit `TYPE_CONDITION_MISMATCH` error with message: `Operator '${op}' requires numeric type (Int or Float), but field '${field}' has type '${type}'`
       - Location: condition's source location (or edge location if condition has no location)
   - `==` and `!=`: valid on all types, no check needed

3. **Remove TD-06 TODO comment**
   - Remove `// TODO: condition type compatibility -- e.g., >= on String fields (v2)` from `src/analyzer/types.ts:54`
   - The TODO is now implemented

**Test targets**:
- Document symbols: file with context, node, memory, graph, edge -> all 5 symbol kinds returned
- Document symbols: empty file -> empty array
- Document symbols: symbol names and kinds correct
- Document symbols: file with parse errors -> symbols for successfully-parsed declarations only
- Condition type: `>=` on Int field -> no error
- Condition type: `>=` on Float field -> no error
- Condition type: `>=` on String field -> TYPE_CONDITION_MISMATCH error
- Condition type: `>=` on Bool field -> TYPE_CONDITION_MISMATCH error
- Condition type: `==` on String field -> no error (equality valid on all types)
- Condition type: `!=` on Bool field -> no error

**Estimated new tests**: ~12
**Estimated agent calls**: 2

## Execution Order

```
R1 (LSP code actions)               <- foundational; introduces workspace scanning infrastructure
  |
R2 (conditional edge routing)       <- independent of R1; can run after R1 for context window efficiency
  |
R3 (document symbols + condition    <- benefits from R1 (uses same ProgramIndex/cache patterns)
     type validation)                  and R2 (condition validation relates to conditional edges)
  |
R4 (integration)                    <- depends on all
```

R1 must be first because it introduces workspace-level file scanning infrastructure that may influence how document symbols accesses ProgramIndex data. R2 is independent but sequenced after R1 for context window efficiency. R3 benefits from both R1 and R2 context. R4 depends on all.
