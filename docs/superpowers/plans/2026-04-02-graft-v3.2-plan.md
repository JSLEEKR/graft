### R1: Parser Error Recovery -- MEDIUM complexity

**Justification**: Fundamental change to the parser contract. The parser moves from throw-on-first-error to error accumulation with panic-mode recovery. This touches parser.ts internals (every parseX function must handle recovery), compiler.ts (must accept ParseResult instead of catching throws), and has downstream effects on LSP diagnostic display. Two agents needed: A2-Pragmatist for minimal implementation, A3-Skeptic for edge cases (nested errors, recovery point ambiguity, partial AST validity).

**Retro items addressed**: R-04 (parser error recovery), R-04a/R-04b/R-04c from design spec.

**Ratchet unlocks required**: 
- [v2.2-R10] "Parser/lexer remain throw-based" -- UNLOCK (parser moves to error accumulation; lexer stays throw-based)

**Agent assignment**:
- Step 1: A2-Pragmatist + A3-Skeptic (2 agents, with adversarial checklist per R-PROC-04+R-PROC-10)
- Step 2: Removed (R-PROC-08)
- Step 3+4: Convergence + Implementation (1 agent, merged)
- Step 5: Reviewer (1 agent)

**Scope**:

1. **ParseResult return type** (R-04b)
   - Define `ParseResult = { program: Program | null, errors: GraftError[] }`
   - Parser class exposes `parse(): ParseResult` instead of `parse(): Program`
   - On zero errors: `{ program, errors: [] }` (backward compatible behavior)
   - On recoverable errors: `{ program (partial), errors: [...] }` -- program has all successfully-parsed declarations
   - On unrecoverable errors: `{ program: null, errors: [...] }` -- only if no declarations can be parsed at all

2. **Panic-mode recovery at declaration boundaries** (R-04a)
   - When parser encounters unexpected token inside a declaration body, it:
     1. Records GraftError with PARSE_UNEXPECTED_TOKEN or PARSE_MISSING_FIELD
     2. Calls `synchronize()` -- advances tokens until next top-level keyword (Context, Node, Memory, Graph, Edge, Import) or EOF
     3. Resumes normal dispatch in the top-level parse loop
   - Recovery points are unambiguous because all Graft declarations start with distinct keywords
   - The `synchronize()` function is ~10 lines: `while (!isAtEnd() && !isDeclarationKeyword(peek())) advance()`

3. **Error accumulation in parser** (R-04b)
   - Add `private errors: GraftError[] = []` field to Parser class
   - Replace `throw new GraftError(...)` with `this.errors.push(new GraftError(...)); this.synchronize()` at recovery-safe points
   - Keep `throw` for truly unrecoverable situations (e.g., lexer produced no tokens) -- catch at top level of `parse()`
   - Each parseX function must decide: recover or propagate. Rule: recover at declaration level, propagate inside expressions/field lists

4. **compiler.ts integration** (R-04c)
   - `compileToProgram()` currently wraps parser in try-catch. Change to:
     ```
     const { program, errors } = new Parser(tokens).parse();
     diagnostics.push(...errors.map(e => toDiagnostic(e)));
     if (!program) return { program: null, diagnostics };
     // continue with analyzer on partial program
     ```
   - Analyzer runs on partial program -- it already accumulates errors and handles missing references gracefully
   - LSP: no changes needed. `validateDocument()` already maps all diagnostics to LSP Diagnostic objects

5. **Partial Program validity** (R-04b)
   - A partial Program must be structurally valid: all fields present, arrays may be shorter than source intended
   - Declarations that failed mid-parse are omitted entirely (not half-populated)
   - This is achieved by the recovery strategy: if parseNode() fails, the node is not added to `program.nodes`

**Test targets**:
- Single error: file with one syntax error shows exactly that error
- Multiple errors: file with 3 syntax errors in different declarations shows all 3
- Recovery: error in first context, valid node after it -- node is present in partial program
- Error + analyzer: parse error + scope error both appear in diagnostics
- Existing valid programs: zero behavior change (ParseResult with empty errors array)
- Edge cases: error at EOF, error in first token, consecutive errors, error in import statement
- LSP integration: multi-error file shows all squiggles simultaneously

**Estimated new tests**: ~18
**Estimated agent calls**: 4

### R2: LSP Polish -- DIRECT

**Justification**: Four independent, well-scoped LSP improvements. Each follows established patterns from v3.1-R1 (completions) and v2.2-R4 (LSP server). No new abstractions. All are additive to existing handler functions. DIRECT tier per R-PROC-01.

**Retro items addressed**: TD-01 (import completion wiring), TD-04 (storage completions), TD-02 (cache eviction), R-11 (keyword hover)

**Ratchet unlocks**: None.

**Agent assignment** (DIRECT tier):
- Step 3+4: Implementer (1 agent)
- Step 5: Reviewer (1 agent)

**Scope**:

1. **Wire resolveImportNames in server.ts** (TD-01)
   - server.ts completion handler (line ~116-121) currently passes no `resolveImportNames` callback to `getCompletions()`
   - Implement the callback: given an import path string, resolve it relative to the current document URI, read + parse the target file, return exported names (contexts + nodes per v2.0-R13)
   - Use existing `resolve()` function from resolver.ts (or a lightweight version that only extracts names)
   - features.ts `getCompletions()` already handles the callback at line ~216-224 -- no changes needed there

2. **Add storage: completions** (TD-04)
   - Add completion context detection for `storage:` keyword in features.ts
   - Currently only valid value is `file` -- offer it as the single completion item
   - Pattern: check if line prefix matches `/^\s*storage:\s*/` and cursor is after the colon
   - Future-proof: when new storage types are added, add them to the completion list

3. **LRU cache eviction** (TD-02)
   - server.ts `cache` Map (line ~18) grows without bound
   - Add access-time tracking: change cache value to `{ program, index, lastAccess: number }`
   - On cache set, if cache.size > MAX_CACHE_SIZE (default 50), evict the entry with oldest lastAccess
   - On cache get, update lastAccess
   - Apply same pattern to `importDeps` Map (line ~21)
   - Simple implementation: iterate map to find oldest entry. O(n) eviction is fine for n <= 50.

4. **Keyword hover documentation** (R-11)
   - Extend `getHoverInfo()` in features.ts to recognize Graft keywords at cursor position
   - Keywords: context, node, memory, graph, edge, import, reads, writes, produces, model, max_tokens, on_failure, storage, foreach, parallel
   - Return documentation string describing the keyword's purpose and basic syntax
   - Reuse documentation text from completion snippets where available (v3.1-R1 already wrote snippet docs)
   - Pattern: check word at cursor position against keyword set before checking ProgramIndex lookups

**Test targets**:
- Import completions: import brace position with resolvable path returns exported names
- Import completions: unresolvable path returns empty list (graceful degradation)
- Storage completions: cursor after `storage:` offers `file`
- Cache eviction: adding 51st entry evicts oldest
- Cache access updates lastAccess timestamp
- Keyword hover: each keyword returns non-empty documentation
- Keyword hover: non-keyword identifiers still resolve via ProgramIndex (no regression)

**Estimated new tests**: ~14
**Estimated agent calls**: 2

### R3: Tech Debt + Bug Fixes -- DIRECT

**Justification**: Three independent mechanical fixes. Each has clear before/after with no design decisions. DIRECT tier per R-PROC-01.

**Retro items addressed**: TD-05 (duplicate JSON writes), TD-06-retro (./format export), Q-04 (test consolidation)

**Ratchet unlocks**: None.

**Agent assignment** (DIRECT tier):
- Step 3+4: Implementer (1 agent)
- Step 5: Reviewer (1 agent)

**Scope**:

1. **Eliminate duplicate JSON writes in executor** (TD-05)
   - `storeOutput()` writes both `nodename.json` and `producesname.json`
   - When node name equals produces name, content is identical -- skip the second write
   - Guard: `if (producesName !== nodeName) { writeFileSync(producesPath, ...) }`
   - Zero behavior change for downstream consumers (both files exist when names differ; single file when same)

2. **Add ./format sub-path export** (TD-06-retro)
   - Add `"./format"` to package.json exports: `{ "import": "./dist/format.js", "types": "./dist/format.d.ts" }`
   - `formatTokenReport()` is the public API from src/format.ts (v3.1-R3)
   - Enables `import { formatTokenReport } from '@graft-lang/graft/format'`

3. **Test file consolidation** (Q-04)
   - Rename test files from version-based naming to feature-area naming where unclear
   - This is a file rename + import update, no test logic changes
   - Goal: new contributors can find tests by feature, not by version history
   - Scope limited to files where the version-based name is actively confusing (e.g., `v2.2-r3.test.ts` could be `scope-warnings.test.ts`)
   - Do NOT rename files where the current name is already descriptive

**Test targets**:
- Executor: single write when node name equals produces name (verify via mock/spy)
- Executor: two writes when names differ (no regression)
- ./format import resolves correctly (packaging test)
- All existing tests pass after renames (zero-regression)

**Estimated new tests**: ~4
**Estimated agent calls**: 2

## Execution Order

```
R1 (parser error recovery)      <- foundational; R2 LSP benefits from multi-error
  |
R2 (LSP polish)                 <- benefits from R1 (multi-error diagnostics)
  |
R3 (tech debt + fixes)          <- independent of R1/R2
  |
R4 (integration)                <- depends on all
```

R1 must precede R2 because the LSP improvements in R2 (especially import completions) benefit from seeing all parse errors at once. R3 is independent but sequenced after R2 for context window efficiency. R4 depends on all.
