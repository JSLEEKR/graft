# Graft v3.0 Implementation Plan

## Overview

Multi-backend codegen + field-level writes + multi-field partial reads + failure strategies + pipeline split. 8 rounds with process improvements from v2.2 retrospective.

**Starting point**: 376 tests, 132 ratchets (v2.2 complete).

### R1: Pipeline Split + ProgramIndex Threading — MEDIUM complexity

**Justification**: Refactoring with clear before/after. `compile()` split is mechanical (extract inner stages into `compileToProgram()`). ProgramIndex threading passes an existing object through function signatures. No new algorithms, no new dependencies.

**Retro items addressed**: RD-06 (LSP calls full compile), RD-14 (compile includes codegen), TD-01 (ProgramIndex redundant construction), RD-07 (executor constructs own ProgramIndex)

**Ratchet unlocks**: None (creates new functions, does not change locked behavior).

**Agent assignment**:
- Step 0: Skipped (incremental refactoring — RP-02)
- Step 1: A2-Pragmatist + A3-Skeptic (2 agents — R-PROC-05)
- Step 2: Score-gated (R-PROC-01) — likely skipped for refactoring
- Step 3: Convergence (1 agent)
- Step 4: Implementer (1 agent)
- Step 5: Reviewer + memory update (1 agent — R-PROC-02)

**Scope**:

1. **Split compile() into compileToProgram() + compileAndGenerate()** (P-01)
   - `compileToProgram(source, filePath)` → `ProgramResult` (lex, parse, resolve, scope, type, estimate)
   - `compileAndGenerate(source, filePath, options?)` → `CompileResult` (compileToProgram + generate)
   - Keep `compile()` as deprecated alias for `compileAndGenerate()`
   - LSP server.ts calls `compileToProgram()` instead of `compile()`

2. **Construct ProgramIndex once, thread through pipeline** (P-02)
   - ProgramIndex constructed in `compileToProgram()` after resolve
   - Passed to ScopeChecker, TypeChecker, TokenEstimator as constructor arg
   - Passed to Executor via `CompileResult` or `ProgramResult`
   - Remove independent ProgramIndex construction in each stage

3. **Extract RuntimeState interface** (Q-07, RD-05)
   - Common `RuntimeState { outputs, input }` interface
   - PromptContext and FlowContext extend it

**Test targets**:
- All 376 existing tests pass (zero-regression refactoring)
- `compileToProgram()` returns program + diagnostics without generating files
- `compileAndGenerate()` returns files (backward compat)
- LSP uses compileToProgram (verify no codegen triggered)

**Estimated new tests**: ~8
**Estimated agent calls**: 5

### R2: AST + Parser Changes for Writes and Reads — HIGH complexity

**Justification**: Pervasive AST type changes (`ContextRef.field` and `NodeDecl.writes`) ripple through every consumer. Parser changes for two new syntaxes (dotted writes, brace reads). Four agents needed because AST type changes affect 10+ files and the parser changes interact with the existing tokenizer. A3's edge-case focus is critical for backward compatibility.

**Retro items addressed**: EXT-02 (field-level writes parser/AST), EXT-03 (multi-field reads parser/AST)

**Ratchet unlocks**: None (AST types are not ratchet-locked; only consumers are).

**Agent assignment**:
- Step 0: Skipped (no new dependencies — R-PROC-04, RP-02)
- Step 1: A1-Architect + A2-Pragmatist + A3-Skeptic + A4-Specialist (4 agents)
- Step 2: Score-gated (R-PROC-01)
- Step 3: Convergence (1 agent)
- Step 4: Implementer (1 agent)
- Step 5: Reviewer + memory update (1 agent — R-PROC-02)

**Scope**:

1. **WriteRef type and writes parser** (F-01, F-02)
   - New `WriteRef` interface: `{ memory: string, field?: string, location: SourceLocation }`
   - `NodeDecl.writes: WriteRef[]` (replaces `string[]`)
   - Parser: `parseWrites()` handles `Memory.field` dotted syntax
   - Backward compat: `writes: [Memory]` (no dot) produces `WriteRef { memory: "Memory", field: undefined }`

2. **ContextRef.field to string[]** (M-01, M-02)
   - `ContextRef.field: string[] | undefined` (replaces `string | undefined`)
   - Parser: `parseReads()` handles `Context.{field1, field2}` brace syntax
   - Backward compat: `Context.field` produces `ContextRef { field: ["field"] }`
   - Backward compat: `Context` produces `ContextRef { field: undefined }`

3. **Update all AST consumers** for new types
   - ScopeChecker: update field validation for `string[]`
   - TypeChecker: update type checking for `WriteRef[]` and `string[]`
   - TokenEstimator: update estimation (handled more in R4)
   - Codegen agents.ts: update reads formatting
   - Runtime prompt-builder.ts: update resolveField
   - LSP features.ts: update hover for multi-field

**Test targets**:
- Parser: `writes: [M.f1, M.f2]` produces WriteRef array, `writes: [M]` backward compat
- Parser: `reads: [C.{f1, f2}]` produces ContextRef with field array, `reads: [C.f]` backward compat
- All existing parser tests pass with new types (backward compatibility)
- All existing analyzer tests pass (consumers updated)
- Codegen: reads formatting with multi-field
- Runtime: resolveField with multi-field

**Estimated new tests**: ~24
**Estimated agent calls**: 7

### R4: Field-Level Analyzer + Estimator — MEDIUM complexity

**Justification**: Extends existing ScopeChecker and TypeChecker with new validation rules. Field-level maps in ProgramIndex are mechanical (same pattern as existing maps). TokenEstimator multi-field logic is a formula change. Two agents sufficient because the patterns are established.

**Retro items addressed**: TD-02 (duplicate field-set construction), EXT-02 (field-level writes analyzer), EXT-03 (multi-field reads estimator), F-03, F-04, M-03

**Ratchet unlocks**:
- REVISIT-01 / v2.2-R05: TypeChecker migrated to ProgramIndex (field maps now available)

**Agent assignment**:
- Step 0: Skipped (extends existing analyzer patterns — RP-02)
- Step 1: A2-Pragmatist + A3-Skeptic (2 agents — R-PROC-05)
- Step 2: Score-gated (R-PROC-01)
- Step 3: Convergence (1 agent)
- Step 4: Implementer (1 agent)
- Step 5: Reviewer + memory update (1 agent — R-PROC-02)

**Scope**:

1. **ProgramIndex field-level maps** (P-03 continued)
   - `producesFieldsMap: Map<string, Map<string, TypeExpr>>` — fields per produces type
   - `memoryFieldsMap: Map<string, Map<string, TypeExpr>>` — fields per memory type
   - ScopeChecker and TypeChecker use these instead of building own maps

2. **ScopeChecker: field-level write validation** (F-03)
   - `checkNodeWrites()`: validate each `WriteRef.field` exists in target memory schema
   - Error code: `SCOPE_INVALID_WRITE_FIELD`
   - Whole-memory writes (field undefined) skip field validation

3. **TypeChecker: per-field overlap** (F-04)
   - `checkWritesSchemaOverlap()`: check at field granularity
   - Two nodes writing to `Memory.field1` and `Memory.field2` is NOT an overlap
   - Two nodes writing to `Memory.field1` IS an overlap → warning
   - Error code: `TYPE_WRITE_FIELD_OVERLAP`

4. **TokenEstimator: multi-field** (M-03)
   - `PARTIAL_FIELD_FACTOR * fieldCount` instead of `PARTIAL_FIELD_FACTOR * 1`
   - When `ContextRef.field` is array of length N, multiply by N

**Test targets**:
- ScopeChecker: writes to valid field (pass), writes to invalid field (SCOPE_INVALID_WRITE_FIELD)
- TypeChecker: two nodes write same field (warning), different fields (no warning)
- TypeChecker: whole-memory write overlaps with field write (warning)
- TokenEstimator: single-field partial read estimate, multi-field estimate (N * factor)
- ProgramIndex field maps: field lookup by produces/memory name

**Estimated new tests**: ~16
**Estimated agent calls**: 5

### R5: Failure Strategies — HIGH complexity

**Justification**: New language feature touching parser, AST, analyzer, and runtime. Failure strategies change the core execution model (abort-on-failure → configurable). Four agents needed: A1 for FlowContext architecture, A2 for minimal viable implementation, A3 for failure mode edge cases (retry exhaustion during foreach, fallback chains), A4 for runtime semantics.

**Retro items addressed**: RD-09 (FlowContext extension), v1.2-R07 (abort-on-failure MVP), EC-07 (on_failure.node validation), S-01 through S-05

**Ratchet unlocks**:
- v1.2-R07: Abort-on-failure MVP → replaced by configurable strategies

**Agent assignment**:
- Step 0: Skipped (no new external deps — R-PROC-04)
- Step 1: A1-Architect + A2-Pragmatist + A3-Skeptic + A4-Specialist (4 agents)
- Step 2: Score-gated (R-PROC-01)
- Step 3: Convergence (1 agent — writes full code for FlowContext per RP-05)
- Step 4: Implementer (1 agent)
- Step 5: Reviewer + memory update (1 agent — R-PROC-02)

**Scope**:

1. **Parser: on_failure clause** (S-03)
   - `on_failure: retry(3)` | `on_failure: fallback(NodeName)` | `on_failure: skip`
   - Optional clause in node declaration (defaults to abort)
   - Lexer: `OnFailure`, `Retry`, `Fallback`, `Skip` keywords

2. **AST: FailureStrategy type** (S-03)
   - `type FailureStrategy = { kind: 'abort' } | { kind: 'retry', count: number } | { kind: 'fallback', node: string } | { kind: 'skip' }`
   - `NodeDecl.onFailure?: FailureStrategy`

3. **ScopeChecker: validate fallback references** (S-04, EC-07)
   - `checkFailureStrategies()`: validate fallback node name exists in nodeNames
   - Error code: `SCOPE_INVALID_FALLBACK`

4. **FlowContext extension** (S-02)
   - Per-node `onFailure` from NodeDecl
   - `executeFlowNodes`: retry loop, fallback dispatch, skip handling
   - Error codes: `RUNTIME_RETRY_EXHAUSTED`, `RUNTIME_FALLBACK_FAILED`, `RUNTIME_SKIPPED`

5. **Runtime: pluggable spawner abstraction** (B-05, EXT-05)
   - `InferenceRequest` interface (backend-agnostic)
   - `SpawnerFn` updated to accept `InferenceRequest`
   - ClaudeCodeBackend's spawner translates to CLI args

**Test targets**:
- Parser: on_failure: retry(3), fallback(Node), skip, absent (defaults to abort)
- ScopeChecker: fallback to existing node (pass), fallback to nonexistent node (SCOPE_INVALID_FALLBACK)
- Runtime: retry succeeds on 2nd attempt, retry exhausted (RUNTIME_RETRY_EXHAUSTED)
- Runtime: fallback executes alternate node, fallback also fails (RUNTIME_FALLBACK_FAILED)
- Runtime: skip produces null output, downstream handles null
- Runtime: default abort behavior unchanged (backward compat)

**Estimated new tests**: ~22
**Estimated agent calls**: 7

## Execution Order

```
R1 (pipeline split + ProgramIndex threading)
  │
  ├── R2 (AST + parser: writes/reads)          ← depends on R1 (ProgramIndex threading)
  │     │
  │     R4 (field-level analyzer + estimator)    ← depends on R2 (WriteRef, ContextRef changes)
  │     │
  │     R7 (runtime field writes + LSP)          ← depends on R2 (types) + R4 (analyzer)
  │
  ├── R3 (CodegenBackend + ClaudeCodeBackend)   ← depends on R1 (ProgramIndex passed to generate)
  │
  ├── R5 (failure strategies)                    ← depends on R1 (RuntimeState) + R2 (AST patterns)
  │
  R6 (quality + cleanup)                         ← depends on R2 (SourceLocation), R5 (error codes)
  │
  R8 (integration + regression)                  ← depends on all
```

Critical path: R1 → R2 → R4 → R7 → R8
Parallel-eligible after R2: R3 and R5 (if R1 is done)
R6 can run after R5 (needs RUNTIME_ error codes) but is independent of R3/R4/R7.

Sequential execution order:
```
R1 → R2 → R3 → R4 → R5 → R6 → R7 → R8
```

R3 (backend) is placed between R2 and R4 because:
- It depends on R1 (ProgramIndex threading) which is done
- It does NOT depend on R2's analyzer changes
- Placing it here gives time before R4 (which uses ProgramIndex field maps that R3 adds graphMap to)
