## Round Details

### R1: formatExpr Extraction + Condition->Expr AST Unification (MEDIUM)

**Why MEDIUM**: This round makes two coupled AST-level changes that affect every pipeline stage (parser, analyzer, codegen, runtime, LSP, tests). The formatExpr extraction is trivial alone but is a prerequisite for the Condition unification (codegen needs formatExpr for condition display). Two agents should debate the Condition->Expr migration strategy -- specifically the test migration approach and whether to update ConditionalBranch.condition and Transform filter in the same commit or separately.

**Retro references**:
- TD-01: formatExpr duplication (technical retro) -- extract to src/format.ts
- Design retro 1D: Condition type legacy friction -- unify into Expr
- E-06: Condition LHS limited to field_access -- resolved by using full Expr
- v4.0-R03: Condition.left: Expr -- subsumes this ratchet (Condition removed entirely)

**Files to modify**:
- `src/format.ts` -- add formatExpr (move from hover.ts)
- `src/lsp/features/hover.ts` -- remove formatExpr, import from format.ts
- `src/codegen/orchestration.ts` -- remove private formatExpr, import from format.ts
- `src/parser/ast.ts` -- remove Condition interface, remove conditionFieldName(), update ConditionalBranch and Transform types
- `src/parser/parser.ts` -- parseCondition returns binary Expr instead of Condition
- `src/analyzer/types.ts` -- checkConditionTypes operates on Expr
- `src/analyzer/scope.ts` -- condition validation uses Expr
- `src/codegen/hooks.ts` -- condition display uses formatExpr
- `tests/helpers.ts` -- mkCond() returns binary Expr

**Test file**: `tests/v50-r1.test.ts`
- formatExpr import from format.ts works
- formatExpr handles all 8 Expr kinds (verify no regression)
- Condition-as-Expr: edge condition parsed as binary Expr
- ConditionalBranch.condition is now Expr | undefined
- Transform filter condition is now Expr
- conditionFieldName function no longer exists
- mkCond() helper produces binary Expr
- Type checker validates conditions via Expr path
- Scope checker validates condition field references via Expr path

**Estimated tests**: ~25

### R2: evaluateCondition/evalCondition Removal (DIRECT)

**Why DIRECT**: With F2 complete from R1, the evaluation functions are straightforward replacements. Each call site of evaluateCondition/evalCondition switches to evaluateExpr. The root cause analysis is already done (TD-04, design retro 2B) and the fix is mechanical.

**Retro references**:
- TD-04: evaluateCondition does not use evaluateExpr for LHS (technical retro)
- Design retro 2B: evaluateCondition/evalCondition as boundary blur
- v3.3-R06: evaluateCondition exported -- function now removed
- v4.2-R11: evalCondition loose equality -- function now removed

**Files to modify**:
- `src/runtime/flow-runner.ts` -- remove evaluateCondition function, update conditional branch evaluation to use evaluateExpr on the binary Expr condition
- `src/runtime/transforms.ts` -- remove evalCondition function, update filter transform to use evaluateExpr
- `src/runtime/expr-eval.ts` -- potentially adjust evaluateExpr to handle the outputs/variables pattern that evaluateCondition used (variable-first resolution is already there)

**Test file**: `tests/v50-r2.test.ts`
- Conditional edge routing still works (field >= value)
- Conditional edge routing with all 6 operators (==, !=, >=, >, <=, <)
- Filter transform with condition still works
- Variable-first resolution in conditions preserved
- Multi-segment field access in conditions preserved (resolveNestedField)
- Undefined field in condition: behavior preserved
- evaluateCondition no longer exported from flow-runner.ts
- evalCondition no longer exported from transforms.ts

**Estimated tests**: ~15

### R3: Expression Polish (DIRECT)

**Why DIRECT**: Both changes are small, well-scoped, and have no design ambiguity. Strict equality is a 2-line change. Exhaustive switches are mechanical additions.

**Retro references**:
- TD-03: Loose equality in evaluateExpr (technical retro)
- R-REVISIT-02: Loose equality semantics worth revisiting (technical retro)
- P-05: Exhaustive switch with never default (technical retro)
- Design retro 1A: Exhaustive switch mandate for Expr dispatchers

**Subpart A: Strict Equality**

**Files to modify**:
- `src/runtime/expr-eval.ts` -- change `==` to `===` and `!=` to `!==` (lines 68-69)
- Update any tests that relied on loose equality behavior

**Behavioral changes to verify**:
- `0 === false` is `false` (was `true` with `==`)
- `"" === false` is `false` (was `true`)
- `null === undefined` is `false` (was `true`)
- `null === null` is `true` (unchanged)
- `5 === 5` is `true` (unchanged)

**Ratchet impact**: v4.5-R04 UNLOCKED (loose equality replaced with strict)

**Subpart B: Exhaustive Switch Mandate**

**Files to modify**:
- `src/runtime/expr-eval.ts` -- add `never` default to evaluateExpr switch
- `src/analyzer/graph-checker.ts` -- add `never` default to checkExprSources switch
- `src/analyzer/types.ts` -- add `never` default to inferExprType and checkExprTypeErrors switches
- `src/format.ts` -- add `never` default to formatExpr switch (after R1 extraction)

**Test file**: `tests/v50-r3.test.ts`
- Strict equality: 0 !== false, "" !== false, null !== undefined
- Strict equality: same-type comparisons still work (5 == 5, "a" == "a")
- Strict equality in edge conditions (after R2 unified evaluation)
- Verify TypeScript compilation passes (exhaustive switches)

**Estimated tests**: ~12

## Process Configuration for v5.0

### Tier Assignments (per process retro 5.1)

| Tier | Rounds | Justification |
|------|--------|---------------|
| MEDIUM | R1 | AST-level change across all pipeline stages. Two agents debate migration strategy. |
| DIRECT | R2, R3, R4 | Mechanical follow-ups with documented root causes. |
| TEST-ONLY | R5 | Cross-feature integration verification. |

### Artifact Policy (per process retro 5.7)

| Round | Artifacts |
|-------|-----------|
| R1 (MEDIUM) | Convergence summary in common_memory |
| R2-R4 (DIRECT) | Review feedback in common_memory only |
| R5 (TEST-ONLY) | Test count + findings in common_memory only |

### Session Strategy (per process retro 5.6)

Execute all 5 rounds in a single continuous session. R1 (MEDIUM) runs first while context is fresh. R2-R5 follow as DIRECT/TEST-ONLY with minimal overhead.

### Lightweight Dissent (per process retro 5.3)

For R1 (MEDIUM), the second agent must include a "risk register" with 2-3 concrete failure scenarios in their analysis.
