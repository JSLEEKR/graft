# Graft v2.2 Implementation Plan

## Overview

npm distribution + LSP server + tech debt cleanup. 6 rounds with process improvements from v2.1 retrospective.

**Starting point**: 288 tests, 107 ratchets (v2.1 complete).

## Process Improvements Applied (from v2.1 Retro-Process)

| ID | Improvement | Applied how |
|----|-------------|-------------|
| R-PROC-01 | Score-gated cross-critique | Cross-critique triggered only when Step 1 score range > 2 |
| R-PROC-02 | Merge Step 6 into Step 5 | Reviewer verifies common_memory update as part of review checklist |
| R-PROC-03 | Adversarial test proposals implemented | Implementer adds reviewer's adversarial test in same round |
| R-PROC-04 | TEST-ONLY tier at 2 agent calls | R6 uses TEST-ONLY tier |
| R-PROC-05 | Accept partial convergence compliance | Reviewers may PASS with PARTIAL items when justified |
| R-PROC-06 | Calibrate test estimates by round type | Estimates follow: refactoring=0, fixes=2-3/fix, new subsystem=5-8/component, integration=1-2/concern |
| R-PROC-07 | Track adversarial test proposals in common_memory | Unimplemented proposals tracked; carried forward or closed |
| RP-02 | Skip Step 0 for incremental rounds | R1, R2, R3 skip Step 0. R4 (LSP) uses Step 0 (new domain) |
| RP-04 | Specs describe WHAT to test, not test helper code | Test targets listed as descriptions |
| RP-05 | Convergence code only for critical sections | Only R4 (LSP) convergence writes full code |

### R1: Tech Debt — Double-Parse + Version + ProgramIndex — MEDIUM complexity

**Justification**: Well-defined refactoring tasks with clear before/after. Double-parse elimination changes one function signature. Version derivation is mechanical. ProgramIndex is a new utility but follows the established Map-based lookup pattern (P-01). No architectural ambiguity.

**Retro items addressed**: TD-01/RD-01 (double-parse), TD-02/RT-06 (version strings), TD-05/P-01 (ProgramIndex)

**Agent assignment**:
- Step 0: Skipped (incremental, extends existing patterns — RP-02)
- Step 1: A2-Pragmatist + A3-Skeptic (2 agents)
- Step 2: Score-gated (R-PROC-01) — likely skipped for refactoring
- Step 3: Convergence (1 agent)
- Step 4: Implementer (1 agent)
- Step 5: Reviewer + memory update (1 agent — R-PROC-02)

**Scope**:

1. **Eliminate double-parse in compiler.ts** (TD-01, RD-01)
   - Change `resolve()` signature: accept `Program` + `sourceFile` instead of `source` + `sourceFile`
   - Update `compiler.ts` to pass already-parsed `program` to `resolve()`
   - Resolver skips entry-file parse, still parses imported files internally
   - All existing import tests must pass unchanged

2. **Version derivation from package.json** (TD-02, RT-06)
   - Create `src/version.ts` that reads version from `package.json`
   - Update `src/index.ts`: replace `'1.2.0'` with `VERSION`
   - Update `src/codegen/settings.ts`: replace `'0.1.0'` with `VERSION`

3. **ProgramIndex utility class** (TD-05, P-01)
   - Create `src/program-index.ts` with Map-based lookups for all declaration types
   - Migrate `ScopeChecker`, `TypeChecker`, `TokenEstimator` to use ProgramIndex
   - Migrate `Executor` to use ProgramIndex
   - Verify all Array.find() hot paths (PQ-01) are eliminated

**Test targets** (per R-PROC-06: refactoring = ~0 new tests):
- All 288 existing tests pass unchanged (zero-regression refactoring)
- Version string test: CLI reports correct version, settings.json contains correct version
- ProgramIndex unit tests: lookup by name, missing name returns undefined, edge map grouping

**Estimated new tests**: ~6 (version + ProgramIndex units)
**Estimated agent calls**: 5

### R2: Tech Debt — Executor Decomposition + Error Codes — MEDIUM complexity

**Justification**: Mechanical extraction with clear module boundaries. Executor decomposition follows the same pattern as v2.1-R1's memory extraction. Error codes are additive (no existing behavior changes). Two independent tasks in the same round because neither affects the other's files.

**Retro items addressed**: A-02 (executor decomposition), A-03 (error codes), D-04 (structured error codes for LSP)

**Agent assignment**:
- Step 0: Skipped (incremental — RP-02)
- Step 1: A2-Pragmatist + A4-Specialist (2 agents)
- Step 2: Score-gated (R-PROC-01) — likely skipped
- Step 3: Convergence (1 agent)
- Step 4: Implementer (1 agent)
- Step 5: Reviewer + memory update (1 agent — R-PROC-02)

**Scope**:

1. **Decompose executor.ts** (A-02)
   - Extract `src/runtime/prompt-builder.ts`: `buildPrompt()`, `buildContextSection()`
   - Extract `src/runtime/flow-runner.ts`: `runSequential()`, `runParallel()`, `runForeach()`
   - Executor delegates to these modules, reduced from ~475 to ~275 lines
   - Use ProgramIndex from R1

2. **Structured error codes** (A-03, D-04)
   - Add `GraftErrorCode` union type to `src/errors/diagnostics.ts`
   - Add optional `code` field to `GraftError` constructor
   - Add codes to all existing ScopeChecker diagnostics (SCOPE_*)
   - Add codes to all existing TypeChecker diagnostics (TYPE_*)
   - Add codes to resolver errors (IMPORT_*)
   - Backward compatible: `code` is optional

**Test targets** (per R-PROC-06: refactoring = ~0 new, codes = 2-3/fix):
- All 288+ existing tests pass (executor decomposition is pure extraction)
- Error code tests: verify specific codes appear on specific diagnostics
- Prompt-builder unit tests: isolated prompt generation without executor

**Estimated new tests**: ~8 (error code assertions + prompt-builder units)
**Estimated agent calls**: 5

### R3: Correctness Fixes — MEDIUM complexity

**Justification**: Four independent, well-defined analyzer checks. Each is a single-function addition with clear test cases. No design ambiguity — the retro-technical already specifies exactly what to check and what to emit.

**Retro items addressed**: EC-01 (foreach binding collision), EC-03 (conditional edge transforms), EC-02 (multiple graphs), TD-04/RD-04 (loadMemory verbose)

**Agent assignment**:
- Step 0: Skipped (incremental — RP-02)
- Step 1: A3-Skeptic + A4-Specialist (2 agents)
- Step 2: Score-gated (R-PROC-01) — likely skipped
- Step 3: Convergence (1 agent)
- Step 4: Implementer (1 agent)
- Step 5: Reviewer + memory update (1 agent — R-PROC-02)

**Scope**:

1. **Foreach binding name collision detection** (C-01, EC-01)
   - In ScopeChecker: check foreach binding against nodeNames, producesNames, contextNames, memoryNames
   - Warning diagnostic with code `SCOPE_BINDING_COLLISION`

2. **Conditional edge transform warning** (C-02, EC-03)
   - In analyzer: when edge has non-direct target and transforms.length > 0
   - Warning diagnostic with code `TRANSFORM_ON_CONDITIONAL`

3. **Multiple graph warning** (C-03, EC-02)
   - In analyzer: when program.graphs.length > 1
   - Warning diagnostic with code `GRAPH_MULTIPLE`

4. **loadMemory verbose warning on corrupt** (C-04, TD-04, RD-04)
   - Add `options?: { verbose?: boolean }` param to `loadMemory`
   - Log warning when file exists but JSON is invalid
   - Update executor to pass verbose option

5. **Source file tracking** (D-05, A-01)
   - Add `sourceFile?: string` to `ContextDecl` and `NodeDecl` in ast.ts
   - Resolver sets `sourceFile` on merged declarations
   - Prerequisite for LSP go-to-definition in R4

**Test targets** (per R-PROC-06: 2-3 tests per fix):
- Foreach binding collision: binding matches node name (warning), binding matches context (warning), unique binding (no warning)
- Conditional edge transforms: transform on conditional edge (warning), transform on direct edge (no warning)
- Multiple graphs: 2 graphs (warning), 1 graph (no warning)
- loadMemory corrupt: corrupt JSON with verbose=true (warning logged), corrupt with verbose=false (silent)
- Source file tracking: imported decl has sourceFile set, entry decl has sourceFile set

**Estimated new tests**: ~14
**Estimated agent calls**: 5

### R4: LSP Server — HIGH complexity

**Justification**: New domain (Language Server Protocol) with external dependency integration. Requires Step 0 research for LSP patterns and `vscode-languageserver` API. Multiple design decisions: connection lifecycle, document sync strategy, hover content format. A3-Skeptic historically catches integration boundary issues.

**Retro items addressed**: L-01 through L-04 (LSP server, diagnostics, hover, go-to-definition)

**Agent assignment**:
- Step 0: 2 agents (R-Architecture: LSP protocol patterns; R-Implementation: vscode-languageserver API)
- Step 1: A1-Architect + A2-Pragmatist + A3-Skeptic + A4-Specialist (4 agents)
- Step 2: Score-gated (R-PROC-01) — likely triggered for new domain
- Step 3: Convergence (1 agent, reads A3-Skeptic first per RP-08)
- Step 4: Implementer (1 agent)
- Step 5: Reviewer + memory update (1 agent — R-PROC-02)

**Scope**:

1. **LSP server module** (L-01)
   - `src/lsp/server.ts`: standalone entry point using `vscode-languageserver`
   - JSON-RPC over stdio
   - Full document sync (TextDocumentSyncKind.Full)
   - `bin.graft-lsp` entry in package.json

2. **Diagnostics** (L-02)
   - Convert `GraftError` to LSP `Diagnostic` on document open/change
   - Map severity, location (SourceLocation to Range), and error code
   - Re-validate on each document change

3. **Hover info** (L-03)
   - Context: show field list with types, max_tokens
   - Node: show model, budget, reads, writes, produces summary
   - Memory: show field list, max_tokens, storage
   - Uses ProgramIndex for O(1) lookups

4. **Go-to-definition** (L-04)
   - Navigate to declaration for identifiers in reads/writes/import lists
   - Cross-file navigation via `sourceFile` on declarations (D-05 from R3)
   - Uses ProgramIndex

**Test targets** (per R-PROC-06: 5-8 tests per component):
- Diagnostics: valid .gft produces no diagnostics, invalid .gft produces error diagnostics, warnings surface as DiagnosticSeverity.Warning
- Hover: hover on context name shows fields, hover on node name shows config, hover on non-identifier returns null
- Go-to-definition: definition of local context, definition of imported node (cross-file), definition of undefined name (null)
- Connection lifecycle: initialize returns capabilities, document open triggers validation

**Estimated new tests**: ~20
**Estimated agent calls**: 10 (2 research + 4 analysis + 0-4 cross-critique + 1 convergence + 1 impl + 1 review)

## Execution Order

```
R1 (tech debt: double-parse + version + ProgramIndex)
  │
R2 (tech debt: executor decomposition + error codes)    ← depends on R1 (ProgramIndex)
  │
R3 (correctness: 4 analyzer checks + source tracking)   ← depends on R2 (error codes)
  │
R4 (LSP server)                                          ← depends on R1 (ProgramIndex), R2 (error codes), R3 (source tracking)
  │
R5 (npm distribution + VS Code extension)                ← depends on R4 (LSP binary for bin entry)
  │
R6 (integration + regression)                            ← depends on all
```

R1 must precede R2 (ProgramIndex needed for executor decomposition).
R2 must precede R3 (error codes needed for new diagnostics).
R3 must precede R4 (source file tracking needed for go-to-definition).
R4 must precede R5 (LSP binary needed for package.json bin entry).
R6 is terminal integration.
