# Graft v3.1 Implementation Plan

## Overview

LSP completions + programmatic API + bug fixes + tech debt cleanup. 5 rounds with process improvements from v3.0 retrospective. Minor version: no new syntax, no breaking changes.

**Starting point**: 477 tests, 168 ratchets (v3.0 complete).

## Process Improvements Applied (from v3.0 Retro-Process)

| ID | Improvement | Applied how |
|----|-------------|-------------|
| R-PROC-01 | Formalize DIRECT tier | NEW. Rounds with no new abstractions, additive to established patterns, or mechanical refactoring skip debate entirely. Applied to R2, R3, R4. Validated by v3.0 R5-R8 (all passed first try with zero debate). |
| R-PROC-02 | Merge Steps 3 and 4 | NEW. In MEDIUM+ rounds, the convergence agent also implements. Eliminates context loss between convergence and implementation. Applied to R1. |
| R-PROC-03 | Kill Step 0 permanently | NEW. Step 0 (Research) has not been run since v2.0. Removed from all round definitions. Only resurrected for genuinely novel subsystems (e.g., WASM compilation). |
| R-PROC-04 | Adversarial checklist replaces forced dissent | NEW. All Step 1 agents receive a standard checklist: (1) silent data corruption paths, (2) type coercion traps, (3) backward compatibility breaks, (4) missing error paths, (5) concurrency hazards. Replaces forced dissenter mechanism which had zero impact in v3.0. |
| R-PROC-05 | Context window budget: max 4 debated rounds | Unchanged. v3.1 uses only 1 debated round (R1), well under budget. |
| R-PROC-06 | Score-gated cross-critique (threshold=2) | Unchanged from v2.2. Applied to R1 if triggered. |
| R-PROC-07 | TEST-ONLY tier at 2 agent calls | Unchanged. Applied to R5. |
| R-PROC-08 | A3-Skeptic mandatory in MEDIUM rounds | Unchanged from v3.0. Applied to R1. |

### R1: LSP Completion Provider — MEDIUM complexity

**Justification**: New LSP capability touching server.ts and features.ts. Completion context detection (where is the cursor?) requires understanding the partial-parse state of the document. A3-Skeptic is valuable for edge cases (cursor mid-token, incomplete declarations, files with parse errors). Two agents sufficient because the LSP architecture is established from v2.2-R4 and v3.0-R7.

**Retro items addressed**: R-03 (deferred from v3.0), Q-02 (LSP editing experience)

**Ratchet unlocks**: None.

**Agent assignment**:
- Step 1: A2-Pragmatist + A3-Skeptic (2 agents, with adversarial checklist per R-PROC-04)
- Step 2: Score-gated (R-PROC-06) — likely skipped
- Step 3+4: Convergence + Implementation (1 agent, merged per R-PROC-02)
- Step 5: Reviewer + memory update (1 agent)

**Scope**:

1. **Completion handler registration** (L-01)
   - Register `CompletionRequest` handler in `src/lsp/server.ts`
   - Add `completionProvider: { triggerCharacters: ['.', '[', '{'] }` to server capabilities
   - Dispatch to `getCompletions(document, position, cache)` in `src/lsp/features.ts`

2. **Cursor context detection** (L-01, L-02, L-03)
   - Analyze text before cursor to determine completion context:
     - Top-level → keyword completions
     - Inside `reads: [` → context/memory name completions
     - After `Name.` → field completions from ProgramIndex field maps
     - Inside `writes: [` → memory name completions
     - Inside graph flow → node name completions
     - After `model:` → model alias completions
     - After `on_failure:` → strategy keyword completions
     - Inside `fallback(` → node name completions
   - Use line text + simple regex, not full re-parse (LSP must be fast)

3. **Name and field completions from ProgramIndex** (L-02, L-03)
   - Use cached `{ program, index }` from compile-on-change (v2.2-R20)
   - Context names from `index.contextMap.keys()`
   - Memory names from `index.memoryMap.keys()`
   - Node names from `index.nodeMap.keys()`
   - Fields from `index.producesFieldsMap.get(name)` and `index.memoryFieldsMap.get(name)`

4. **Import name completions** (L-04)
   - When cursor is inside `import { ... } from "path"`, resolve the import path
   - Offer names exported by the resolved file (contexts + nodes per v2.0-R13)
   - Gracefully degrade if import path is incomplete or unresolvable

5. **Snippet completions for declarations** (L-05)
   - `node` → expands to node block template with model, reads, produces
   - `context` → expands to context block template with fields
   - `memory` → expands to memory block template with fields and storage
   - Use `InsertTextFormat.Snippet` with tab stops

**Test targets**:
- Keyword completions at top level
- Name completions inside reads/writes lists
- Field completions after dot (context and memory)
- Model alias completions after `model:`
- Strategy completions after `on_failure:`
- Node name completions inside graph flow
- Graceful behavior on files with parse errors (stale cache used)
- No completions in comment blocks
- Import name completions

**Estimated new tests**: ~18
**Estimated agent calls**: 4

### R2: Parallel Failure Strategy Fix + Fallback Cycle Detection — DIRECT

**Justification**: Two well-defined bug fixes with clear before/after. TD-04 is a single call-site change in flow-runner.ts. E-05 is a graph cycle detection algorithm (same pattern as import circular detection in v2.0-R14). No new abstractions, no design decisions. DIRECT tier validated by v3.0 R5-R8 (similar scope items passed first try without debate).

**Retro items addressed**: TD-04 (parallel bypasses failure strategies), E-05 (circular fallback references)

**Ratchet unlocks**: None.

**Agent assignment** (DIRECT tier):
- Step 3+4: Implementer (1 agent)
- Step 5: Reviewer (1 agent)

**Scope**:

1. **Parallel branches use executeWithFailureStrategy** (B-01, TD-04)
   - `flow-runner.ts:81-84`: replace `ctx.executeNode(t)` with `executeWithFailureStrategy(t, ctx)`
   - Each parallel target respects its node's `on_failure` declaration
   - If a parallel node has `on_failure: retry(3)`, it retries within the parallel block
   - If a parallel node has `on_failure: skip`, its output is null (downstream handles)

2. **Fallback cycle detection** (B-02, B-03, E-05)
   - Add `checkFallbackCycles()` in ScopeChecker (called from `checkFailureStrategies()`)
   - Build fallback edge graph: `Map<string, string>` (node → fallback target)
   - DFS with in-stack set to detect cycles (mirrors v2.0-R14 import cycle pattern)
   - Self-reference: `on_failure: fallback(self)` → immediate cycle
   - Mutual: A → B → A → cycle detected at A
   - Error code: `SCOPE_FALLBACK_CYCLE` added to ScopeErrorCode sub-union
   - GraftErrorCode union updated (follows v3.0-R25 sub-union pattern)

**Test targets**:
- Parallel node with `on_failure: retry(N)` retries within parallel block
- Parallel node with `on_failure: skip` produces null output
- Parallel node with `on_failure: fallback(X)` executes fallback
- Self-referencing fallback → SCOPE_FALLBACK_CYCLE error
- Mutual fallback cycle (A→B→A) → SCOPE_FALLBACK_CYCLE error
- Chain without cycle (A→B→C, no cycle) → no error
- Existing non-parallel failure strategy tests still pass

**Estimated new tests**: ~10
**Estimated agent calls**: 2

### R3: Tech Debt Cleanup — DIRECT

**Justification**: Four independent mechanical cleanups. Each has a clear before/after with no design decisions. All follow established patterns. DIRECT tier per R-PROC-01.

**Retro items addressed**: TD-01 (Executor duplicates ProgramIndex state), TD-02 (ScopeChecker duplicates ProgramIndex state), TD-03 (CLI formatting duplication), TD-05 (stale version in error message)

**Ratchet unlocks**: None (internal refactoring only).

**Agent assignment** (DIRECT tier):
- Step 3+4: Implementer (1 agent)
- Step 5: Reviewer (1 agent)

**Scope**:

1. **Executor: remove duplicate state** (D-01, TD-01)
   - Remove `this.nodeMap` and `this.edgeMap` fields from Executor
   - Replace all `this.nodeMap` references with `this.index.nodeMap`
   - Replace all `this.edgeMap` references with `this.index.edgesBySource`
   - Zero behavior change — pure alias removal

2. **ScopeChecker: derive from ProgramIndex** (D-02, TD-02)
   - Remove `this.contextNames`, `this.nodeNames`, `this.memoryNames` Sets
   - Replace `this.contextNames.has(x)` with `this.index.contextMap.has(x)`
   - Replace `this.nodeNames.has(x)` with `this.index.nodeMap.has(x)`
   - Replace `this.memoryNames.has(x)` with `this.index.memoryMap.has(x)`
   - Zero behavior change — source of truth consolidation

3. **CLI: extract formatTokenReport()** (D-03, TD-03)
   - Extract token report printing logic from compile and check commands into shared function
   - `function formatTokenReport(report: TokenReport): string`
   - Both commands call the shared function
   - Zero behavior change — deduplication

4. **Foreach nesting error message** (D-04, TD-05)
   - Update "not supported in v1.1" to reference current version or remove version reference
   - Use `VERSION` constant from `src/constants.ts` or simply say "not supported"

**Test targets**:
- All existing tests pass (zero-regression refactoring)
- Executor uses index.nodeMap exclusively (verify via grep — no this.nodeMap references remain)
- ScopeChecker uses index maps exclusively (no this.contextNames/nodeNames/memoryNames)
- CLI compile and check produce identical token report output

**Estimated new tests**: ~4 (primarily regression)
**Estimated agent calls**: 2

## Execution Order

```
R1 (LSP completions)         ← independent, uses existing ProgramIndex
  │
R2 (parallel fix + cycles)   ← independent of R1
  │
R3 (tech debt cleanup)       ← independent of R1, R2
  │
R4 (API surface)             ← independent of R1-R3 (package.json + types file)
  │
R5 (integration)             ← depends on all
```

All of R1-R4 are independent and could theoretically run in parallel. Sequential execution is used because DIRECT rounds are fast (2 calls each) and context window budget is not a concern with only 1 debated round.
