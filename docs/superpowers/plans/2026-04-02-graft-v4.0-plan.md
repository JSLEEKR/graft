## Rounds

### R1: Lexer + AST + Expression Parser (HIGH)

**Justification for HIGH**: New AST types (Expr union, FlowNode 'let' kind, FlowNode 'graph_call' kind, GraphParam, GraphArg), new tokens (Plus, Minus, Bang), new keyword (let), and a recursive descent expression parser. This is the most architecturally significant round -- the Expr type design and parser precedence rules will be ratchet-locked and affect all downstream rounds. 4-agent debate justified: expression grammar design has genuine alternatives (operator set, precedence levels, field access syntax).

**Apply R-PROC-14**: Wait for all agent analyses before convergence.
**Apply R-PROC-18**: Convergence spec must list error path tests.
**Apply R-PROC-20**: Convergence spec must cross-reference plan test targets.

**Scope**:
- Add `Plus` (+), `Minus` (-), `Bang` (!) tokens to TokenType enum and KEYWORDS/symbol handling in lexer
- Add `Let` keyword to TokenType enum and KEYWORDS map
- Define `Expr` discriminated union in ast.ts (5 kinds: literal, field_access, binary, unary, group)
- Define `GraphParam` and `GraphArg` interfaces in ast.ts
- Extend `FlowNode` union with `let` kind and `graph_call` kind
- Extend `GraphDecl` with `params: GraphParam[]`
- Update `Condition` interface: replace `field: string` with `left: Expr`
- Implement `parseExpr()`, `parseAdditive()`, `parseUnary()`, `parsePrimary()` in parser.ts
- Implement `let` parsing in `parseFlowNode()`
- Implement graph parameter parsing in `parseGraphDecl()`
- Implement graph call parsing (identifier + `(` disambiguation) in `parseFlowNode()`
- Update condition parsing to use `parseExpr()` for the left-hand side
- All existing 890 tests must continue passing (Condition.field migration)

**Migration for Condition.field**:
- Replace `Condition.field: string` with `Condition.left: Expr` throughout the codebase
- All existing condition creation sites (parser, tests) must construct `{ kind: 'field_access', segments: [field] }` instead of bare field strings
- All existing condition consumption sites (evaluateCondition, scope checker, type checker, estimator) must extract the field from `condition.left`
- This is a codebase-wide change and must be done atomically in this round

**Test target**: ~18 new tests
- Expr parsing: literal (number, string, boolean), field access (single, multi-segment), binary (+, -, /), unary (-, !), grouped expression, nested binary
- Let parsing: `let x = literal`, `let x = Node.field`, `let x = expr`
- Graph param parsing: no params (backward compat), single param, multiple params, default values, Node type param
- Graph call parsing: `GraphName(arg: value)`, multiple args, no args error
- Condition migration: existing condition tests pass with new Expr-based left-hand side
- Error: let with reserved keyword name
- Error: unterminated expression (missing operand)
- Error: graph param with unsupported type

### R2: Scope Checker + Type Checker for Variables and Expressions (MEDIUM)

**Justification for MEDIUM**: New validation rules for variable scoping, expression type inference, and graph parameter checking. Design ambiguity around variable declaration ordering (must variables be after their source node?), graph recursion detection (DFS like import cycles?), and expression type error messages. R-PROC-14 applied.

**Apply R-PROC-14**: Wait for A2+A3 analysis before convergence.
**Apply R-PROC-18**: Convergence spec must list error path tests.
**Apply R-PROC-20**: Convergence spec must cross-reference plan test targets.

**Scope**:
- ScopeChecker: variable name collision detection (nodes, contexts, memories, graphs, other variables)
- ScopeChecker: variable declaration order enforcement (source node must appear before `let` in flow)
- ScopeChecker: variable reference validation in conditions (variable must be declared before use)
- ScopeChecker: graph parameter validation at call sites (required params provided, types match)
- ScopeChecker: recursive graph call detection (DFS with ancestor set, like import cycle detection)
- ScopeChecker: `Node` parameter arguments reference declared nodes
- TypeChecker: expression type inference (literal types, field access types from ProgramIndex, binary operator result types)
- TypeChecker: type mismatch in binary expressions (`+` on incompatible types, `-`/`/` on non-numeric)
- TypeChecker: variable type vs condition usage (numeric variable in ordered comparison, etc.)
- New error codes: SCOPE_VAR_COLLISION, SCOPE_VAR_UNDECLARED, SCOPE_VAR_ORDER, SCOPE_GRAPH_RECURSION, SCOPE_GRAPH_PARAM_MISSING, SCOPE_GRAPH_PARAM_TYPE, TYPE_EXPR_MISMATCH, TYPE_VAR_CONDITION
- Update evaluateCondition tests for Expr-based conditions (if not covered in R1)

**Test target**: ~16 new tests
- Variable collision with node name, context name, memory name, graph name
- Variable declared after source node (valid)
- Variable declared before source node (error: SCOPE_VAR_ORDER)
- Variable referenced in condition before declaration (error: SCOPE_VAR_UNDECLARED)
- Variable referenced in condition after declaration (valid)
- Graph call with all required params (valid)
- Graph call missing required param (error: SCOPE_GRAPH_PARAM_MISSING)
- Graph call with wrong param type (error: SCOPE_GRAPH_PARAM_TYPE)
- Recursive graph call (error: SCOPE_GRAPH_RECURSION)
- Mutual graph recursion A -> B -> A (error)
- Expression type: string + string (valid)
- Expression type: number + string (error: TYPE_EXPR_MISMATCH)
- Expression type: number - number (valid)
- Expression type: number / number (valid)
- Expression type: boolean negation (valid)
- Variable type inferred from field access, validated in condition

### R3: Runtime for Variables and Expressions (MEDIUM)

**Justification for MEDIUM**: New runtime execution paths for `let` evaluation and expression computation. Design ambiguity around expression evaluation in the context of node outputs (how to resolve multi-segment field access against the outputs map), error handling during expression evaluation (what if a referenced field is missing at runtime?), and variable scope lifetime (when are variables cleaned up?).

**Apply R-PROC-14**: Wait for A2+A3 analysis before convergence.
**Apply R-PROC-18**: Convergence spec must list error path tests.
**Apply R-PROC-20**: Convergence spec must cross-reference plan test targets.

**Scope**:
- `evaluateExpr()` function in flow-runner.ts: resolves expressions against the outputs map and variable map
  - `literal`: return value directly
  - `field_access`: resolve segments against outputs map (first segment = node name, remaining = nested field access)
  - `binary`: evaluate left and right, apply operator (+, -, /)
  - `unary`: evaluate operand, apply operator (-, !)
  - `group`: evaluate inner expression
- `executeFlowNodes` handles `let` kind: call evaluateExpr(), store result in variable map
- Variable map: `Map<string, unknown>` passed through flow execution, scoped to graph
- Update `evaluateCondition()` to accept variable map, resolve `field_access` expressions against variables first, then outputs
- `executeFlowNodes` handles `graph_call` kind: resolve parameters, create child variable map, delegate to called graph's flow
- Graph call execution: creates a child scope (fresh variable map with parameter bindings), executes the called graph's flow, returns output
- Error handling: missing field at runtime throws with location information (RUNTIME_FIELD_MISSING or similar)
- All 890+ existing tests must continue passing

**Test target**: ~14 new tests
- Let evaluation: literal value stored in variable map
- Let evaluation: field access from node output
- Let evaluation: binary expression (addition, subtraction, division)
- Let evaluation: unary negation
- Let evaluation: string concatenation
- Variable used in condition: `when score >= 0.7`
- Variable used in condition with else branch
- Graph call: simple parameterized graph execution
- Graph call: Node parameter resolution
- Graph call: primitive parameter (Int) passed and available
- Graph call: default parameter used when not provided
- Graph call: budget isolation (child graph has own budget)
- Error: field access on missing node output (runtime error)
- Error: division by zero handling

### Expected Challenges

1. **Condition.field migration (R1)**: Touching every file that references `Condition.field` is the highest-risk change. Must be atomic -- partial migration will break tests. Strategy: change the type first, fix all compilation errors, then update tests.

2. **Parser growth (R1)**: Adding ~100-150 lines for expression parsing to a 906-line file. If the file exceeds ~1050 lines, consider extracting `parseExpr*` functions to a separate file in a follow-up DIRECT round.

3. **Graph call runtime scoping (R3)**: Child graph execution needs a clean scope boundary -- its own variable map, its own flow position, but access to parent's outputs for parameter resolution. This is the most complex runtime addition since failure strategies (v3.0-R5).

4. **Expression type inference (R2)**: The type checker has been relatively static since v3.0-R4. Adding expression type inference is a genuine extension that may require the TypeChecker to carry a type environment (variable name -> inferred type mapping).
