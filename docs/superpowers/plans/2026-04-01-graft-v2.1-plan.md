# Graft v2.1 Implementation Plan

## Overview

Add real-time token tracking to Graft's runtime engine. Cleanup tech debt and fix correctness gaps from v2.0 retrospective. 4 debate rounds with process improvements from retro.

**Starting point**: 249 tests, 92 ratchets (v2.0 complete).

### R2: Correctness Fixes — MEDIUM complexity

**Justification**: Well-defined validation rules with clear error messages. No architectural decisions. Each fix is independent and testable in isolation.

**Retro items addressed**: RT-03, RT-04, RT-05

**Agent assignment**:
- Step 1: A3-Skeptic + A4-Specialist (2 agents)
- Step 2: A3-Skeptic + A4-Specialist (cross-critique, no forced dissenter)
- Step 3: Convergence (1 agent)
- Step 4: Implementer (1 agent)
- Step 5: Reviewer (1 agent)
- Step 6: Memory update (1 agent)

**Scope**:

1. **Writes schema validation** (RT-03)
   - In `TypeChecker`: for each node with writes, check produces-field-names intersect memory-field-names
   - Warning if zero overlap (not error — saveMemory silently writes nothing)
   - Addresses deferred v2.0-R23

2. **max_tokens > 0 validation** (RT-04)
   - In `ScopeChecker` or `TypeChecker`: validate `MemoryDecl.maxTokens > 0` and `ContextDecl.maxTokens > 0`
   - Error diagnostic (zero/negative max_tokens is always wrong)
   - Addresses deferred v2.0-R10

3. **Parallel memory write detection** (RT-05)
   - In `ScopeChecker.checkGraphFlow`: for each parallel FlowNode, collect writes from all branches
   - Warning if two branches write the same memory name
   - Walk the flow tree recursively (foreach bodies may contain parallel blocks)

**Test targets**:
- Writes schema validation: node writes to memory with overlapping fields (pass), zero overlap (warning)
- max_tokens validation: context/memory with max_tokens 0 (error), negative (error), positive (pass)
- Parallel write detection: two parallel nodes writing same memory (warning), different memories (no warning), nested foreach+parallel (warning)

**Estimated new tests**: ~12
**Estimated agent calls**: 8

### R3: Token Tracking Core — HIGH complexity

**Justification**: New subsystem touching subprocess parsing, executor orchestration, and file I/O. Multiple design choices with correctness implications: CLI output format change, budget enforcement semantics, degradation behavior. A3-Skeptic historically catches critical bugs at integration boundaries.

**Retro items addressed**: RT-07, RT-08, RT-09, RD-06, RD-07

**Agent assignment**:
- Step 1: A1-Architect + A2-Pragmatist + A3-Skeptic + A4-Specialist (4 agents)
- Step 2: 4 agents cross-critique, highest-confidence agent is forced dissenter
- Step 3: Convergence (1 agent, reads A3-Skeptic output first)
- Step 4: Implementer (1 agent)
- Step 5: Reviewer (1 agent, must propose adversarial test)
- Step 6: Memory update (1 agent)

**Scope**:

1. **TokenUsage interface** (RT-07)
   - Add `TokenUsage { inputTokens: number; outputTokens: number }` to `subprocess.ts`
   - Add `tokenUsage?: TokenUsage` to `SpawnResult`
   - Evaluate whether to switch from `--print` to `--output-format json` for structured usage data
   - Parse token usage from CLI output; graceful degradation if unparseable

2. **TokenTracker class** (RT-09)
   - Tracks cumulative token consumption across nodes
   - Records per-node actual vs estimated
   - Exposes `isWarning` (>= 80%) and `isCritical` (>= 90%) thresholds
   - Uses `BUDGET_WARNING_THRESHOLD` and `BUDGET_CRITICAL_THRESHOLD` from constants.ts

3. **Token log writing** (RT-08, RD-06)
   - After each node execution, append to `.graft/token_log.txt`
   - Format: `[timestamp] Node <name> | estimated: <est> | actual: <actual|N/A> | cumulative: <cum>/<budget> (<pct>%)`
   - Append mode (`fs.appendFileSync`); file cleared on session start
   - Co-exists with hook-generated edge transform entries

4. **RunResult token extension** (RD-07)
   - Add `tokenUsage` field to `RunResult` with budget, consumed, fraction, perNode breakdown
   - Extend `NodeTokenReport` with optional `actualIn`, `actualOut`
   - Extend `TokenReport` with optional `actualTotal`

5. **Budget enforcement** (RT-09)
   - Advisory only: log warnings to verbose output at 80%/90% thresholds
   - Populate `RunResult.tokenUsage` for caller inspection
   - No hard abort in v2.1 (caller decides)

**Test targets**:
- TokenUsage parsing: valid JSON with usage field, missing usage field (undefined), malformed output (undefined)
- TokenTracker: recording multiple nodes, cumulative tracking, threshold detection at boundary values
- Token log writing: entries appended in correct format, file created if missing, cleared on session start
- RunResult includes token summary after execution
- Budget thresholds: exactly at 80% (warning), 79.9% (no warning), 90% (critical)
- Graceful degradation: when CLI does not return usage data, estimates used, no crash

**Estimated new tests**: ~20
**Estimated agent calls**: 12

## Execution Order

```
R1 (cleanup) — extract constants, utils, memory.ts
  |
R2 (correctness) — writes validation, max_tokens > 0, parallel write detection
  |
R3 (token tracking core) — TokenUsage, TokenTracker, token log, budget enforcement
  |
R4 (integration) — end-to-end verification, calibration
```

R1 must precede R3 (constants.ts and memory.ts extraction needed before adding token code).
R2 can theoretically run parallel to R1 but sequential is safer (shared analyzer files).
R3 depends on R1 (uses extracted constants).
R4 depends on all previous rounds.
